# 07 前传：这些机制为什么是现在这个样子

> 读 [07-中断与时钟](07-中断与时钟.md) 之前先读这一篇。那一章的每个名词
> （IDT、GDT、TSS、重映射……）都不是发明的，是 40 年里一个问题摞一个
> 问题演化出来的——跳过中间的问题直接看答案，谁都会懵。
> 这篇从"什么都没有"开始，每个问题逼出一个解法，解法又留下新的问题，
> 读完你再到第 07 章动手，那些名词就都有了来历。

## 开场：先退回到最简模型

把一切历史、术语都忘掉，CPU 只干一件事：

```
从内存里取出一条指令 → 执行 → 取下一条 → 执行 → …
```

它有两个与生俱来的限制，后面所有设计都从这两个限制出发：

**第一，它不主动感知外设。** CPU 本体只访问内存和自己的寄存器。键盘、时钟、硬盘——它不会主动得知这些设备的状态。那它们的数据怎么进来？只能 CPU 主动去某个编号的地址（IO 端口）读取。问题立刻出现：**CPU 怎么知道什么时候该去读？** 键盘的按键不是定时发生的。

**第二，它不计时。** CPU 内部没有时钟概念。主循环想按秒做事，得靠外界告诉它"过了一秒了"。同样的问题：**谁来告诉它？**

这两个问题的最笨解法一模一样：**轮询**——CPU 在死循环里不停地读每个设备的状态，检查有没有事件。能跑，但 CPU 的全部时间都耗在轮询上，正经工作干不了多少。80 年代的真实困境就是：机器越做越快、设备越来越多，轮询的代价越来越高。

要摆脱轮询，得让设备能**主动通知** CPU。于是有了"中断"这个概念——本篇的主角。

---

## 第一幕：一根公共请求线（中断的诞生）

最原始的中断，物理上就是一根电线：所有设备共享一根线，谁有事件就把这根线的电平置为有效——CPU 的电路设计成"检测到这根线有效，就暂停当前指令流"。

能通知了，但只知道"有事"，不知道**是谁**、**该干什么**。

解法：通知的同时附带一个编号。设备触发请求线的同时，往一个约定的地方放一个编号（中断号），CPU 被打断后先读编号，再按编号决定干什么。

这个设计到今天没变过，只把"约定的地方"和"按编号决定干什么"制度化成了正式的名词：

- 编号 → **中断号**
- "按编号决定干什么"的对照表 → **IDT**（一张最多 256 行的"中断号 → 处理函数"映射表，第 07 章会亲手填它）

为什么是"查内存里的一张表"而不是把处理逻辑固化在 CPU 里？想想就知道：键盘的处理代码是我们自己写的 Rust 函数，CPU 出厂的时候它还不存在——**处理逻辑只可能放在内存里，CPU 只可能去查表**。表放内存、内容随便填，这叫可编程。

## 第二幕：线不够用了（PIC 的诞生）

一根线，很快不够用：时钟要通知、键盘要通知、磁盘也要通知，大家挤一根线，CPU 分不清是谁。

物理上的解法很直接：**多引几根**。x86 CPU 实际上有两根中断输入（一根可屏蔽、一根不可屏蔽），但设备有十几个——差了一个数量级，全靠 CPU 自己增加引脚不现实。

于是 1981 年，IBM PC 的主板上放了一颗独立的芯片干这活：所有设备把中断线接到**它**身上（15 路，每路一个编号，就是 **IRQ**），它负责汇集、按优先级仲裁，然后去触发 CPU 那一根线，同时把对应的编号递过去。这颗芯片就是 8259，**PIC**。

一句话总结它存在的原因：**CPU 的中断输入引脚是稀缺资源，所以中断需要一颗汇集转发的控制器。** 它是主板上一个真实的、独立于 CPU 的芯片——今天你在 QEMU 里跟它通信，QEMU 在模拟 1981 年那颗真芯片的每一个寄存器。这就是为什么它叫"可编程"中断控制器：它的编号规则（IRQ 编号对应哪个中断号）不是固定的，开机时由软件写进去——这个"写规则"的动作就叫**重映射**（第 07 章动手做）。

顺带把同主板上的另一颗芯片也认了：8253（**PIT**，定时器）。它跟中断系统是配合关系：它的唯一工作是**按设定好的频率**触发 IRQ0 这根线。开场说 CPU 不计时——现在计时的问题由它解决。同样，QEMU 里它在模拟一颗 1981 年的真芯片，"1193182 Hz"是它的晶振频率，出厂就这样。

到这幕结束，硬件侧的全貌凑齐了：

```
设备们 ──各接一根 IRQ 线──► 8259 PIC ──汇总成一根线──► CPU
                                ▲
              8253 PIT 定时器 ──┘（专职触发 IRQ0）
```

## 第三幕：被打断的程序不能察觉（现场的诞生）

现在 CPU 会在任意两条指令之间被夺走执行权。这带来一个极严厉的约束：

**被打断的程序，恢复执行时必须和被中断前一模一样。**

为什么这么苛刻？因为它没法配合——它甚至不知道自己被打断过。它被中断前刚算出 `rax = 42`，恢复后 `rax` 变成了别的值，程序逻辑直接错乱，而且这种错**无法复现、无法调试**（中断什么时候来是随机的）。所以规矩定成"绝对无感"，一点讨价还价的余地都没有。

"一模一样"具体指什么？CPU 执行一条指令的**全部状态**：

- 十几个通用寄存器的值
- 下一条指令的地址（被打断时它正要取的下一条）
- 标志寄存器（上一条指令算出的进位/溢出等标志）
- 栈的位置（它自己的工作现场在栈上）

谁来保存？分工是自然形成的：

**CPU 自动保存**它独知、软件够不着的部分：下一条指令的地址、标志、栈位置——这三样在执行 `iretq`（中断专用的返回指令）时也会被 CPU 自动恢复，软件想插手都插不了。

**软件必须保存**通用寄存器——因为 CPU 一进处理函数就要开始使用寄存器（哪怕只是为了执行"把数据从端口读进来"这种最简单的活），**执行流自己改动的寄存器它有责任恢复**。所以处理函数的入口处得先把所有寄存器的值压到栈上，出口处再按原序恢复。

第一幕说过"查表跳进处理函数"，但跳过去之前还有一道固定的工序：**保存现场**。承担这道工序的代码传统上叫**存根（stub）**——它不处理事件，只做转交：保存现场后把控制权交给真正的处理函数，处理函数返回后反向恢复。第 07 章你会亲手写这段汇编，到时候那十几步 push/pop 不是什么复杂技巧，就是"把寄存器挨个保存、办完事挨个恢复"的纪律而已。

## 第四幕：编号冲突（重映射的来历）

PIC 是 1981 年的产品，它的默认编号规则是：IRQ0~7 对应中断号 **8~15**。当年这个安排毫无问题——8086 那个时代的 CPU 里，0~15 这些编号是空的，随便用。

出问题的是后来。1982 年之后的 80286、80386 引入了**异常**（exception）体系：CPU 执行指令出问题（除零、非法指令、缺页……）时，也走中断那套"报号、查表、跳处理"的机制，编号固定占 **0~31**。从此中断号 0~31 被异常占用，而 PIC 默认的 8~15 正好在被占用的范围里。

这时 PC 已经卖出去几百万台，软件、主板、操作系统全都默认"IRQ 对应 8~15"——改不动了，成了遗产。

于是留给每一个自制操作系统的人一道绕不开的手续：**开机时告诉 PIC "重新编号，从 32 开始"**。这就是重映射——第 07 章里那四组 ICW 配置字节干的就是这件事。现在你能理解为什么"必须做"了：不做，时钟的中断（IRQ0 → 8 号）会被 CPU 当成"双重故障"（8 号异常）处理，整个系统一开机行为就完全错乱。

## 第五幕：段的登记表（GDT 的来历）

前面四幕把中断的传递链条搭完了，但链条的最后一环还悬着一个东西：
CPU 跳进中断处理函数时，要装载新的**代码段寄存器 CS**——CS 是什么？
它背后为什么还站着一张登记表？这两个名词（段、GDT）都不是为中断
发明的，来自另一条完全独立的历史线；这条线和中断在"跳转"这一点上
交汇，所以讲中断之前必须先把它讲清。故事从 1978 年一个和中断毫无
关系的算术问题开始。

**1978 年，8086 时代。** 寄存器 16 位，一个寄存器能表示的数只有
64K，但当时市场想要 1MB 内存。解法：拿两个寄存器拼一个地址——一个
"段地址"左移 4 位，加上一个"偏移"，凑出 20 位的实际地址。段地址
放在 CPU 的几个专用寄存器里：执行代码用 CS（代码段），读写数据用
DS（数据段），栈操作用 SS（栈段）。注意这时候的"段"**纯粹是地址
计算**，没有任何检查：任何程序都能用任何段地址访问任何内存。

**1982 年，80286，保护模式。** 多任务时代来了：好几个程序同住一台机器，"任何程序访问任何内存"等于灾难——你的程序一出错就破坏了别人的数据。解法：给段**登记**。段寄存器不再直接存段地址，改存一个**索引**（这就是"选择子"），CPU 拿索引去查一张**全局描述符表**——表里每行写明"这个段从哪开始、多长、什么权限（只读？可执行？）"。这张表就是 **GDT**（Global Descriptor Table，全局描述符表）。从这一刻起，"越界访问别人的内存"从正常操作变成了 CPU 主动拒绝的违规。

**1985 年，80386，32 位 + 分页。** 段之外又发明了分页（把内存切成固定大小的页、按页翻译地址）——**分页比分段好用得多**（粒度细、支持换出到磁盘）。从此新系统都用页，段只作为兼容机制保留。

**2003 年，x86-64。** 规范直接确定：64 位模式下，段的"基址+长度"字段**全部忽略**，地址翻译全权归页表。分段正式退出历史舞台。

那 GDT 为什么还在？两个残留的正式用途：① 段寄存器还得指向表里某个合法条目——硬件规矩没删干净；② 表里除了"代码段/数据段"这类描述符，还允许挂**别的系统结构**（下一幕的主角 TSS 就挂在 GDT 里）。于是 64 位的 GDT 从"描述所有内存段的大表"缩减成"只有几个条目的小表"——第 07 章我们会建的就是这样一张几行的表。

顺带一个历史细节：**CS 不能用 mov 指令装载**。为什么设计成这样？80286 引入保护模式时，**换段=换权限**，是敏感操作，必须走控制流转移（跳转/返回）让 CPU 有机会做权限检查；mov 只搬数值、不做检查，所以设计者干脆没给段寄存器留 mov 通道。第 07 章遇到装载 CS 时用的绕行办法（构造一次"远返回"），绕开的正是这条 1982 年立下的规矩。

## 第六幕：一个失败的设计（TSS 的来历）

上一幕末尾留了个尾巴：GDT 里除了代码段/数据段，还能挂别的系统
结构。这一幕的主角 **TSS**（任务状态段，Task State Segment）就是
其中之一——它的名字记录着它的失败。

80386 时代，Intel 的设计者有个大目标：**让 CPU 硬件直接管理多任务**。设想中，操作系统只要执行"切换到任务 B"，CPU 就自动把任务 A 的全部寄存器存进一个结构、把任务 B 的全部寄存器装回来——这个保存任务状态的结构就是 TSS，名字里的 T（Task）就是它的本意。

现实是：硬件任务切换太慢（要逐个搬运几十个寄存器），灵活度又差（操作系统的调度策略千变万化，硬件写死的流程跟不上）。所有主流操作系统（Linux、Windows）都**没用它**，全改成软件自己保存/恢复寄存器。设计失败，TSS 从"任务切换中枢"降级成了遗留结构。

但降级时留了两样有用的东西，正好是我们今天要的：

- **RSP0**：从低权限代码进高权限代码时，CPU **必须**换一个栈（权限不同的代码不能共用一个栈，否则低权限代码可以读取/破坏高权限栈的内容）。切换到哪个栈？查 TSS。这是 TSS 在 64 位下的头号正式用途——到第 10 章做用户态时它会真正启用
- **IST**（七格备用栈表）：处理"进入时栈已经损坏"的灾难场面（双重故障）——第 07 章给双重故障配的 16KB 备用栈，挂在的就是这里

所以我们对 TSS 的用法是历史遗留的再利用：一个被时代淘汰的任务切换机构，我们只使用它记录备用栈位置的那部分字段。

## 第七幕：PIC 的两条规则（EOI 与 IMR 的来历）

最后补上 PIC 使用规则里的两条，它们的来历同样直接：

**EOI（中断结束信号）。** PIC 把中断转发给 CPU 之后，默认**不再转发同级别和更低级别的中断**，直到收到"处理完毕"的信号——这是中断优先级机制的必然代价：PIC 得记住"谁还在被服务中"，期间不送同级别和更低级别的中断进来（否则低优先级中断能被高频时钟中断无限打断，得不到执行）。所以"处理完发 EOI"是软件的义务，忘了发就是那根线永久挂起。

**IMR（中断掩码寄存器）。** 15 路 IRQ 不会同时都登记好处理函数——某个 IRQ 的信号到了、IDT 表里对应行是空的，CPU 查表查到空项，直接触发三重故障整机复位。所以规矩是：开机默认全部屏蔽，哪个 IRQ 的处理函数写好了、登记了，再把对应位解除屏蔽（unmask）。出事故的窗口被这条规则堵死。

## 收场：把七幕拼成一台完整的机器

七幕的成果拼起来，就是一条完整的中断链路——现在每个环节你都知道来历，因为你知道它是被哪个问题逼出来的：

```
你敲键
  → 键盘放好编号，触发 IRQ1       （第一幕：让设备能主动通知）
  → 8259 PIC 汇集，报中断号 33     （第二幕：线不够，加控制器；第四幕：重新编号）
  → CPU 暂停，自动保存关键现场      （第三幕：被打断的程序不能察觉）
  → 查 IDT 第 33 行，跳进存根      （第一幕：可编程查表）
  → 存根保存所有寄存器，调用处理函数 （第三幕）
  → 处理函数读端口、处理事件        （第 07 章动手实现的部分）
  → 发 EOI                         （第七幕）
  → 存根恢复寄存器，iretq 返回      （第三幕）
```

以及链路之外的两条关系：GDT/TSS 是分段时代的遗产（第五、六幕），IDT 的表项里引用着它们；PIT 是那颗专职定时触发 IRQ0 的芯片（第二幕）。

接下来去读第 07 章，你看到的就不再是一堆术语，而是一台你知道全部来历的机器。

## 这篇的读法建议

不用背。读两遍：第一遍就是现在，读第 07 章之前，建立"每个东西都有来历"的直觉；第二遍是读完第 07 章之后——那时再看"8086 拼地址""80286 的段登记""80386 的硬件多任务设计"，你写下的每行代码都能对应到一段历史。

真正的操作系统学习，一半是写代码，另一半就是逐步理解这台机器的历史包袱——你今天撞上的每一个"为什么要这么绕"，背后都有一段 40 年前的商业或工程决策。读懂它们，你就和当年那批工程师想到了一起。
