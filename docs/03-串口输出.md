# 03 · 串口输出：让内核打出第一行字

> 上一章：[02-第一个内核](02-第一个内核.md)。内核能编译了，但它没有任何
> 输出手段——跑没跑、卡在哪、死没死，外面一无所知。这一章给它实现
> 第一个输出功能。

## 这一章要做成什么

一句话：**让内核往串口写字节，QEMU 的终端上能看到内核的输出**。

要动两个文件：

- 新建 `kernel/src/serial.rs`——串口驱动，约 90 行
- 修改 `kernel/src/main.rs`——加一行模块声明，kmain 里打两句话

先打个预防针：**本章写完、编译通过之后，还看不到字**。因为内核还是
没人加载的"裸文件"（Limine 还没接上），打印的代码根本没机会执行。
本章的验证标准是编译干净通过；看到字要等下一章第一次开机。之所以
先写它，是因为它是内核的第一件"器官"，而且等 Limine 接上后立刻
就能用。

## 先理清楚：谁在干什么

先看我们要打通的输出链条，一共三个环节：

```
内核（往一个特殊地址写字节）
   → UART 芯片（主板上管串口的芯片，把字节一位一位发出去）
      → QEMU（模拟器捕获这些字节，直接显示在你的终端上）
```

最后一个环节解释了为什么开发期串口这么好用：不用接任何线，QEMU 一条
参数就能把串口内容打到终端。将来真机上，屏幕黑掉的时候，串口日志
往往还能告诉你死在哪一步。

第一个环节有个必须想通的问题：`println!` 能用吗？不能——它是标准库的，
标准库依赖操作系统管屏幕，而我们就是在写操作系统。所以"让内核说话"
意味着**直接跟硬件打交道**。跟哪块硬件？整机里最简单的一块：串口。
屏幕当然也行，但屏幕要自己画像素、画字体，是好几章的工程；串口
几十行代码就通，先用最短路径让内核"能说话"，再说"说得好看"。

## 原理一：串口和 UART 芯片

串口的背后是一块叫 **UART** 的芯片（具体型号 16550），管着第一个
串口 **COM1**——就是老电脑背后那个梯形的 9 针接口。它的工作方式：
你向它写入一个字节，它把这个字节按位逐个发出去；接收端按同样的
规则逐位接收，重组出原来的字节。它在今天 PC 上的主业，就是给
内核当调试输出。

## 原理二：CPU 怎么跟它说话——两套地址空间

x86 有个乍听很怪的设计：**CPU 有两套独立的地址空间**。

- **内存地址空间**——RAM、显存在这里，用普通 `mov` 指令读写；
- **IO 端口空间**——一套独立编址的地址空间，只有 65536 个端口，
  老式外设的寄存器映射在这里，必须用专门的 `in`/`out` 指令、
  指明端口号才能访问。

| | 内存地址空间 | IO 端口空间 |
|---|---|---|
| 访问指令 | `mov`（普通读写） | `in` / `out`（专用指令） |
| 谁在这里 | RAM、显存 | UART、定时器、PS/2 键盘控制器等 |
| 容量 | 按位数定（64 位） | 只有 65536 个端口 |

UART 的端口基址是 **0x3F8**。所以"往串口写一个字节"翻译成硬件动作
就是：执行 `out` 指令，端口 0x3F8，带上那个字节。

> 用 IO 端口访问是老式外设的接法。现代设备（NVMe 硬盘、USB 控制器）
> 大多把寄存器映射进内存空间，用普通 `mov` 访问。两种我们都会遇到，
> 先拿下简单的。

## 原理三：UART 的寄存器

UART 不只有一个端口，而是从 0x3F8 起连着 8 个端口，各负责一项功能。
常用的就 4 个：

| 偏移 | 名字 | 用途 |
|---|---|---|
| +0 | 数据口 | **写**它 = 发一个字节；读它 = 收一个字节 |
| +1 | 中断使能 | 本章全部关掉（0x00），中断是后面章节的事 |
| +3 | 线路控制 | 设数据格式，还包含一个开关位 DLAB（见下） |
| +5 | 线路状态 (LSR) | bit 5 = **发送器空闲**：为 1 时才能写入下一个字节 |

为什么发送前要检查 LSR 的 bit 5？UART 发送有物理速度（每秒几千位），
你写入字节的速度超过它的发送速度，多出来的就丢了。所以每次写入前
先确认上一次发送已经完成——它是这章代码里唯一的"循环等待"。

初始化时还有两件事要办：

- **波特率**：双方约好的发送速度。不一致就会乱码——发送方按一个
  速率发、接收方按另一个速率收，位边界就对不上了。我们用 38400，
  它由一个"除数"决定（除数 3）。
- **DLAB 开关**：UART 的端口号不够用，偏移 0 和 1 被复用了——
  DLAB=0 时它们是数据口和中断使能，把 DLAB 设为 1，同样的两个
  地址就变成波特率除数的低/高字节，设完再清回 0。这是年代久远的
  省地址设计，认识了就不觉得怪。

最后还有 Rust 这关：`out`/`in` 是内联汇编，必然是 `unsafe`。原因是
本质性的：编译器只能验证类型和引用规则，而"往端口 0x3F8 写一个
字节"——那个端口上是不是真有 UART、写入是否安全、要不要先满足
什么时序——编译器一概无法验证。`unsafe` 的含义因此不是"危险的
代码"，而是"编译器无法验证、由程序员担保正确性"的显式标记。内核
开发里满是编译器无法验证的硬件操作，unsafe 会一路相伴；纪律是让
每个 unsafe 块**尽量小**。

原理齐了，开始写代码。按依赖顺序分三步：先写最底层的"递字条"动作，
再包装成串口结构体，最后在 kmain 里说话。

## 动手一：outb / inb——最底层的端口读写

新建 `kernel/src/serial.rs`，先写两个端口读写原语：

```rust
use core::arch::asm;

/// 往 IO 端口写一个字节
pub fn outb(port: u16, value: u8) {
    unsafe {
        // out 指令的固定用法：端口地址放 dx，数据放 al
        asm!("out dx, al",
            in("dx") port,
            in("al") value,
            options(nomem, nostack, preserves_flags),
        );
    }
}

/// 从 IO 端口读一个字节（下一章收键盘数据时会用到）
pub fn inb(port: u16) -> u8 {
    let value: u8;
    unsafe {
        asm!("in al, dx",
            out("al") value,
            in("dx") port,
            options(nomem, nostack, preserves_flags),
        );
    }
    value
}
```

看 `asm!` 的写法：`in("dx") port` 表示"编译前把变量 port 装进 dx
寄存器"，`out("al") value` 表示"执行后把 al 寄存器倒回变量 value"。
`options(...)` 告诉编译器：这段汇编不碰内存、不碰栈、
不改标志位，可以对周围的代码正常优化。

注意两个函数的签名是**安全的**（`pub fn` 而不是 `pub unsafe fn`）：
危险被圈在函数体内部这一小块 unsafe 里，调用者不需要、也不应该
再写 unsafe。这就是"把 unsafe 圈到最小"的落地——**unsafe 只应
出现在真正 unsafe 的地方**。

## 动手二：SerialPort——把寄存器访问包成结构体

继续在 `serial.rs` 里加。初始化把所有寄存器设到正确状态：

```rust
/// 一个串口。base 是它的端口基址（COM1 = 0x3F8）
pub struct SerialPort {
    base: u16,
}

impl SerialPort {
    /// COM1 的标准端口号，IBM PC 时代沿用至今
    pub const COM1: u16 = 0x3F8;

    pub fn new(base: u16) -> Self {
        Self { base }
    }

    /// 初始化：关中断 → 设波特率 → 定格式 → 开缓冲
    pub fn init(&mut self) {
        outb(self.base + 1, 0x00); // 关串口中断
        outb(self.base + 3, 0x80); // DLAB=1：偏移 0/1 变为波特率除数
        outb(self.base + 0, 0x03); // 除数低字节 = 3 → 38400 波特
        outb(self.base + 1, 0x00); // 除数高字节
        outb(self.base + 3, 0x03); // DLAB=0；8 数据位、无校验、1 停止位
        outb(self.base + 2, 0xC7); // 开 FIFO 缓冲并清空
        outb(self.base + 4, 0x0B); // 数据终端就绪 + 请求发送
    }
```

七行 `outb` 对应原理三里说的每一件初始化事项，注释一一对应——
对着上面的寄存器表读一遍就懂。注意 `init` 里**没有 unsafe 块**：
危险已经封在 outb/inb 最底层，上层代码保持干净。

然后是发送：

```rust
    /// 发一个字节。发之前先检查 LSR 的 bit 5（发送器空闲）
    fn send_raw(&mut self, data: u8) {
        // 发送器未空闲就一直等待
        while inb(self.base + 5) & 0x20 == 0 {}
        outb(self.base, data);
    }

    /// 发送字符串。'\n' 自动补 '\r'
    pub fn send_str(&mut self, s: &str) {
        for &b in s.as_bytes() {
            match b {
                b'\n' => {
                    self.send_raw(b'\r');
                    self.send_raw(b'\n');
                }
                _ => self.send_raw(b),
            }
        }
    }
}
```

`send_raw` 里那个空循环叫**忙等待**：反复读状态位，直到发送器空闲。
效率不高但简单可靠，裸机开发的基本功，等有了中断再升级。

`send_str` 里 `\n` 为什么要补 `\r`？历史约定：`\r`（回车）让显示
位置回到行首，`\n`（换行）移到下一行。只发 `\n` 的话，一些串口
终端不执行"回到行首"，后续各行会逐行向右错开。

## 动手三：kmain——内核输出

最后改 `kernel/src/main.rs`，两处：

```rust
mod serial;   // 声明新模块（加在 use 之后）
```

```rust
#[unsafe(no_mangle)]
pub extern "C" fn kmain() -> ! {
    let mut com1 = serial::SerialPort::new(serial::SerialPort::COM1);
    com1.init();
    com1.send_str("\n=== MOS booting ===\n");
    com1.send_str("hello from kernel!\n");

    loop {
        core::hint::spin_loop();
    }
}
```

创建 COM1、初始化、输出两行字——内核的输出代码就这么多。

## 踩坑实录

**`unnecessary unsafe block` 警告。** 最初版本里，`init` 和
`send_raw` 的函数体也包了 unsafe 块，编译器立刻警告。原因很值得
体会：outb/inb 用安全签名封装后，**调用它们的代码里没有任何 unsafe
操作**——包着的全是安全函数，编译器指出这里没有任何需要担保的操作，
unsafe 块是多余的。修法就是上面看到的：unsafe 只存在于 outb/inb
两个函数体内部，审查危险代码只需要看这两个小块。

> 顺带一个反例：如果反过来写 `pub unsafe fn` 再在体内包 unsafe 块，
> 也会报同样的警告——unsafe fn 的函数体默认整块就是 unsafe 的，
> 再包一层属于重复标记。

## 本章小结

- 输出链条：内核写端口 → UART 按位发送 → QEMU 捕获并显示到终端；
  `println!` 不能用，因为标准库依赖操作系统
- x86 两套地址空间：内存（`mov`）和 IO 端口（`in`/`out`）；COM1
  的端口基址 0x3F8
- UART 四个关键寄存器：数据口、中断使能、线路控制（含 DLAB 复用）、
  线路状态（发送器空闲位）
- unsafe 的纪律：范围最小，只存在于最底层，函数签名保持安全

**里程碑**：串口驱动编译通过，内核具备了输出能力 ✅
