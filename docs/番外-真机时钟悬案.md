# 番外篇：真机时钟悬案——一次完整的排障实录

## 这一章讲什么

贪吃蛇（上一篇）在 QEMU 里活蹦乱跳，刻进 U 盘上真机（华硕天选5 Pro，Ventoy 启动）：**蛇不动，按一下键才动一下**。QEMU 与真机行为不一致——这是自制操作系统最值钱的一类 bug，因为它逼你直面真实硬件。

这一篇是排障全过程的实录：怎么设计证据、怎么读证据、踩了什么坑、最后怎么修。它不是教程正文——09 章调度器还等着——但它教的东西（证据链思维、诊断代码的纪律）比任何一章都通用。

## 第一件武器：把证据画到屏幕上

真机的最大困难：**没有串口**。串口日志（第 03 章起一直使用的调试输出通道）在 QEMU 里全部可用，真机上是黑箱——你看不见，它也传不出来。真机上唯一的输出通道是屏幕。

所以第一步不是猜原因，是**实现诊断输出**。游戏画面左上角的灰色诊断行，每个字段读一样硬件实况：

| 字段 | 读的是 | 回答的问题 |
|---|---|---|
| `T=` | 开机滴答数 ÷ 100 | 时钟中断来过吗？（0 = 一次都没有） |
| `P`± | PIT 计数器两次读数是否变化 | PIT 芯片还活着在数数吗？ |
| `M`0/1 | 主 PIC 掩码寄存器的 bit0 | IRQ0 被什么挡住了吗？ |
| `I=`xx | 主 PIC 的 IRR（排队中的中断列表） | IRQ0 的信号有没有到达 PIC？ |

读法各有一番讲究：`P` 的检测要先写"锁存命令"再分两字节读计数器（边计数边直接读会读到不一致的瞬时值）；`I` 读 IRR 前要写 OCW3 声明"我要的是 IRR 不是 ISR"。这些寄存器都只在真机诊断期使用，对应函数留在 `pic.rs`。

一次开机，四个字段，回来的是：**`T=0 P+ M0 I=00`**。

## 证据链推理

四个字段拼起来，范围窄得惊人：

- `P+`：PIT 芯片在数数 → **固件没有停用 8254**
- `M0`：PIC 没有挡 IRQ0 → **掩码没问题，也没有 SMM 偷偷改**
- `I=00`：PIC 的排队名单上从来没有 IRQ0 → **信号根本没走到 PIC 这一层**
- 键盘能用（IRQ1 正常）→ **PIC 和 CPU 收中断的整条路都是好的**

结论：PIT 在动、PIC 在听，唯独 IRQ0 这条中断线没有信号。物理上这条线怎么会断？x86 平台上恰好有对应机制：**HPET 的 legacy replacement 模式**。固件在 HPET 芯片的配置寄存器里设一个位（`LEG_RT_CNF`），语义是"把 8254 的 IRQ0 输出从总线上断开，由 HPET 定时器 0 接管"。如果固件设了这个位却没让 HPET 实际产生中断——两边都失效，恰好对应我们的四个字段。

这是**头号嫌疑**，但确认它需要一次实读：得读到那一位的值。HPET 的寄存器地址写在 ACPI 表里，于是有了本案的第二个工具。

## 教训一：诊断代码自己不许崩（一次冻结事故）

第一版 ACPI 探针顺着 `RSDP → XSDT → HPET 表` 的指针链一路解引用，放在启动路径里。QEMU 跑通了，真机一开机——**屏幕冻在 `pit counting`，游戏没了**。

复盘这个事故，它是两层错误叠加：

1. **对裸指针链的解引用没有防护**。真机的 ACPI 表布局和 QEMU 不同，链上某个指针指向的地址没被映射，一读 → 缺页异常（#PF）。
2. **异常信息只输出到了串口**。我们的异常处理函数打印到串口后停机——QEMU 里看得见，真机上是黑箱。于是缺页的表现是"无声冻结"，屏幕停在出事前最后一行。

教训沉淀成三条纪律（写在 `acpi.rs` 文件头）：

1. **启动路径零新增解引用**——开机只存两个地址（RSDP、HHDM 偏移），纯存数，不可能出错；探测逻辑锁进游戏里的 H 键，不按就永远不执行
2. **读任何陌生地址前先做校验**——内核手里本来就有 UEFI 内存清单（08-1 章），凡是清单上没有的地址一律不碰（`mm::in_ram` / `mm::in_map`）
3. **进度实时上屏**——每步解引用前先打印进度，冻住时屏幕上最后一行就是出错位置

这套纪律的代码就是现在的 `acpi.rs`：`stash()`（开机存数）、`probe()`（探测，全程地址校验+进度输出）、`try_clear()`（C 键触发，L=1 时清位）。（探测起初锁在 H 键后面；第六幕起提前到开机自动跑，敢挪的前提和校验方式的调整见第七幕。）

## 修复：不依赖 IRQ0 的 PIT 轮询

HPET 位这一嫌疑要等下一次开机按 H 才能验证。但游戏不必等结论——**换一条不依赖 IRQ0 的路径获取时序**。

证据中最有价值的是 `P+`：PIT 芯片在计数。中断断了，但**时间本身没有断**。时钟 100Hz、每 10ms 计数器数满一圈——主循环只要自己读计数器，就能拿到和中断一致的时序。这落在 `interrupts.rs` 的 `poll_pit_fallback()`。它最终实现为三级降级结构（每级的来历见第四、五、六幕）：

```
主循环每轮：
  ├─ HPET 主计数器活着？→ 用它维护滴答计数（出厂定死频率，首选）
  ├─ ACPI PM 定时器活着？→ 用它维护滴答计数（备用时钟）
  └─ 都没有 → 盯 PIT 计数器（老路），且每轮验证 IRQ0 死活：
       真滴答落后"应有拍数"（= PIT 重装数）3 拍以上 → 轮询接管产生滴答
```

"落后 3 拍接管"这个判据也换过两版，换的原因本身就是案情——见第五幕。

### 第一版为什么慢：数事件，事件会丢

第一版轮询数的是"重装"这个**事件**，每数到一次 `TICKS += 1`。QEMU 里完美，真机上**蛇明显偏慢**。

原因：事件会丢。现代笔记本的固件会通过 SMM（系统管理模式）随时占用 CPU 几毫秒，处理自身事务（风扇、温度、电池），CPU 不在的那段时间里计数器照样转，但**没有代码观测到它转过了几圈**——漏几圈蛇就慢几分。QEMU 没有 SMM，模拟不出这种丢失，所以虚拟机里永远测不出来。

### 第二版：记时间，不数事件

修法是把"数事件"换成"记时间"：每次轮询读计数器，**两次读数的差值**就是这段时间走过的 PIT 时钟数，累加起来除以除数 = 现在应该是第几拍。差值会自动把 CPU 缺席期间的时间补上——只要两次轮询的间隔小于一个周期（10ms），分毫不差；就算丢了一个周期的轮询，下一次差值也把它找回来。（这个前提后来在真机上死了，见下文第三幕。）

配套还有两个精确性修正：

1. **PIT 从方波模式（mode 3）换成速率发生器（mode 2）**。mode 3 每个时钟计数 -2、重装值还在两种数之间交替，"计数值差"换算不成干净的时间；mode 2 每时钟正好 -1、重装永远回到除数值，差值才是精确的时钟数。
2. **绕圈的差值要用 PIT 的周期取模**。一次写错成 `u32` 回绕减法再取模——`2^32` 不是除数的倍数，每次重装多记约一拍，秒表跳着走（模拟环境里 4 秒后直接跳 10 秒）。正确写法是 `prev + 除数 - c` 再按除数取模，重装那一跳自动落在差值里。

接管后给滴答赋值用的是 `fetch_max`（取最大）而不是 `fetch_add`（累加）：万一哪天 IRQ0 恢复（比如将来按 C 真把线接回去了），中断和轮询同时修改这个计数器，累加会变成两倍速，取最大则始终与真实时间一致。

### 第三幕：前提也会死——真机上蛇还是慢

第二版交上真机，蛇自己爬了——但**明显偏慢**，QEMU 里却分毫不差。这次的问题不在公式，在公式脚下踩着的前提：

> "只要两次轮询间隔小于一个周期（10ms）就分毫不差。"

QEMU 里这个前提永远成立：画布 4MB、"显存"就是普通内存，每步棋的整屏翻页亚毫秒完成。真机上每步要把 **16MB 拷进显存**，而显存写入慢（要经过显卡），一拷就是几十毫秒——主循环耗费在拷贝里的这段时间，PIT 计数器已经多次重装，而两次读数的差**最多只能累计一个周期的计数**，多转的时间整段丢失。每秒 1000ms 真实时间，计数上只记了约 250ms——蛇慢成四分之一。

**教训：验证一个修复，要连它注释里的前提一起验证。** 公式在 QEMU 里测得再准，前提在真机上死了，修复就是空的。

两处修改，一处消除症状，一处改进机制：

1. **脏矩形翻页**（game.rs + console.rs）：每像素行一面脏旗，翻页只拷画过的行。中间还踩了一脚：第一版只记一条 `[最小行,最大行]` 的脏带，HUD 锚在屏顶、蛇在屏中，一条带把大半个屏圈进去，还是慢——改成逐行旗标、连续脏行拼段拷贝，拷贝量从 16MB 缩到 0.7MB。
2. **量程扩容**（pic.rs + interrupts.rs）：轮询接管时把 PIT 除数设为最大值 65535，周期从 10ms 放宽到 54.9ms。计数器读数看不出转了几圈，那就让它转得慢一点——55ms 以内的停顿（慢显存拷贝、SMM 占用 CPU）都能完整累计。滴答的换算基准不变：换算常数固定为 11931 时钟/拍，与当前除数解耦。

### 诊断手段自己也会误导：KVM 的 PIT 怪癖

验证第二处修改时遇到一个插曲，差点造成误判：给主循环注入"每圈被占用 30ms"的模拟停顿后，QEMU（KVM 加速）里时钟**随机冻结**——有时 8 秒、有时 13 秒、有时开机就冻。加诊断输出追查：累计时钟数精确到千分之一秒地自洽，主循环的滴答累计却在某一轮突然停止——卡死点在"高频读 PIT 计数器"的循环里。换纯软件模拟（TCG，QEMU 用户态模拟的 PIT）跑 300 秒，零冻结，时间分毫不差。

结论：冻结是 **KVM 内核态 PIT 仿真的怪癖**（访客高频锁存/读计数器会使它停止计数），不是内核的问题。真机上是真 8254 硬件，计数器自由运行，读它不会让它停——此前真机上 T= 持续增长也证明连续轮询在真机上是有效的。这个插曲本身是一课：**诊断读数异常时，先分清是"被测系统有故障"还是"运行诊断的环境本身有缺陷"**。

### 怎么在不上真机的情况下验证

修"真机才有的 bug"成本最高的就是每次验证都要重启。本案的做法是在 QEMU 里**制造同款故障**：把 `pic::unmask(0)` 这行注释掉——IRQ0 被挡住，恰好复现真机的"信号到不了"。第三幕又增加一项：在翻页里按拷贝字节数注入忙等，模拟真机慢显存（16MB 拷 458ms）。断言逐条跑：

- 正常路径：中断活着，轮询只旁观，秒表每秒一跳、不多不少（防"轮询多算"）
- 模拟真机：中断死了 + 慢显存，20ms 内接管，秒表照样每秒一跳、一秒不跳（防"轮询少算"——第一、二幕的两次事故都是这么抓出来的）
- 加码：每圈主循环再注入 30ms 的"SMM 占用 CPU"停顿，量程扩容后时间依然分毫不差

三条都过，再交真机。

## 第四幕：蛇慢成五分之一——跳变的滴答与等值判断冲突

第三幕的两刀交上真机：蛇爬了，但**还是明显偏慢**，面板上的 `T=` 也比虚拟机里涨得慢。

盯一个数字就能破案：量程扩容把 PIT 周期放宽到 54.9ms 后，轮询代码是"每次计数器重装才把滴答同步一次"——一次同步让 `TICKS` 直接跳 5.49 拍（54.9 ÷ 10）。而游戏的步点判断写的是：

```rust
if t % STEP_INTERVAL == 0 { self.tick(); }
```

等值判断有个隐藏前提：**滴答是一拍一拍涨的**。中断正常时确实如此；轮询同步后滴答是跳着涨的——从 12 直接跳到 17，中间的 20、10 一个都不会"等于"。一秒里本该有 10 个步点，等值判断只能命中跳变恰好落在倍数上的一两个——蛇慢成五分之一。

这是第三幕自己引入的问题：扩大量程和步点判断互相冲突。两处都要修：

1. **轮询侧**：别攒到重装才同步——每次轮询都把"应有拍数"顶进 `TICKS`（`fetch_max`），滴答的涨幅恢复平滑。
2. **游戏侧**：等值判断换成"到点就走"——记下一个步点 `next_step`，`t >= next_step` 就走一步并顺延。跨过去的步点不补（补会连跳几步），从当前拍重新数节拍。

## 第五幕：接管判据的盲区——"活着但慢"的中断

第四幕交真机：还是慢，`T` 涨得"非常的缓慢"。面板读数 `T=0 P+ M0 I=00 L- F0 B5`——注意 **F0**：轮询从没接管。

回头检查判据才发现它的盲区。当时的判据是"连续两圈重装没见到滴答涨"（20ms 无滴答 = 失效），它能抓**完全失效**的中断，抓不住**活着但慢**的中断——比如固件把节拍定成了 20Hz，每圈之间总有一次中断到达，"连续两圈无中断"的条件永远凑不齐。

第五幕换判据：数重装。周期 10ms 下每重装一次 = 本该走一拍，"重装数"就是此刻应有的拍数。**真滴答落后应有拍数 3 拍以上** = 这条中断线不可信——失效了、被屏蔽了、活着但周期被改慢了，一律接管。正常线最多瞬时落后 1 拍，永远达不到 3，QEMU 不会误接管。落后判据对失效、变慢两种情形一律成立。

可真机上 F0 依旧、T 依旧慢。这次的读数指向更深的一层：**重装数和滴答数在同步变慢**。两条参考线——IRQ0 的节奏、PIT 重装的节奏——全都来自同一颗 PIT。如果它的实际周期根本不是我们写进去的 10ms（除数被谁改了，头号嫌疑仍是 SMM），那"滴答落后重装数"就永远凑不出 3 拍，判据永远不触发。**同源的数据无法互相验证——它们出自同一颗可编程时钟，会一起出错。** 只要时间计数还记在 PIT 身上，怎么交叉验证都是白费。

## 第六幕：架构转向——时间计数换用 free-running 时钟源

查 Linux 内核的时钟子系统（clocksource 架构）得到的定论：**真正的操作系统从不依赖"可编程的"定时器**。PIT 的除数是软件写进去的，固件（SMM）同样能写——这样的时钟源既可能被改快也可能被改慢。Linux 信任的是另一类时钟源：**free-running 计数器**——频率出厂固定、只增不减、没有谁能在运行中改它的节奏。

MOS 采用同样的思路，时间计数按三级降级：

1. **HPET 主计数器**（首选）：频率出厂定死（刻度周期写在能力寄存器里，单位飞秒），64 位只增不减——没有量程问题、没有回绕误差，两次轮询间隔多长都不丢时间。
2. **ACPI PM 定时器**（备用）：2000 年后的每台机器都有，频率出厂固定 3.579545 MHz，从 FADT 表里查到它的 IO 端口。24 位计数器每 4.68 秒回绕一圈，差值按掩码取模就绕过去了——前提只剩"轮询间隔小于 4.68 秒"，对主循环绰绰有余。而且它走 IO 端口，**端口读永不缺页**，连地址校验都不需要。
3. **PIT 轮询**（兜底）：前两个时钟源都不可用的机器才轮到它。

主计数器的开关（总配置寄存器 bit0）在探测时顺手打开。探测也从"游戏里按 H"提前到**开机流程里自动跑**——敢进启动路径的理由：全程地址校验兜底、任何失败只打印一句然后放弃（绝不 panic）、整条路在 QEMU（q35+OVMF 有 HPET 表）先验证过。

面板新增 **A 字段**记录时间计数使用哪个时钟源：`AH` = HPET、`AP` = PM 定时器、`A-` = 两者都不可用（退回 PIT）。

## 第七幕：连环坑实录——A0 的四层嵌套问题

第六幕的代码交真机：**A0**——HPET 探测压根没成。而 QEMU 里居然也是 `AP`：连模拟器都没走通 HPET 路径。嫌疑从"真机特殊性"转向"代码自身缺陷"。

这回换排查方法：把探测的每一步进度**同时打进串口**（`trace` 双通道：屏幕给人看，串口给调试看），QEMU 无头跑——`-display none -serial file:日志文件`，跑 30 秒读日志，全程不碰截图。四层问题逐层定位：

**坑 1：真机把 ACPI 表放"保留区"。** 探测的第一道校验 `mm::in_ram` 只认 usable/ACPI 类内存区段，而真机固件常把 RSDP 放在 **reserved 类**——QEMU/OVMF 放的是 ACPI 可回收类，所以虚拟机全部通过、真机第一步就被拦下。reserved 也是真内存（固件留着自用而已，读它不会缺页），校验对 kind 1 放行。这是"QEMU 里测不出真机前提"的又一次重演。

**坑 2：HPET 的 MMIO 不在内存清单里。** 解决坑 1 后 QEMU 日志显示：`hpet regs not in memmap, too risky, STOP`。0xFED00000 是芯片组 MMIO 区域，OVMF 的内存清单里根本没有这段。清单外 = 可能没被映射 = 缺页风险——但这回是判断过于保守：把校验临时改成"警告但继续"做实验，读得动、内核存活、时钟照跳。结论：**Limine 的 HHDM 把全部物理空间（包括清单外的 MMIO 区域）都映射好了**，内存清单检查对 MMIO 降级为"知情记录"。

**坑 3：HPET 表地址字段偏移数错。** 坑 2 解决后，日志立刻暴露直接原因：`hpet regs @0`——寄存器基址是 0！HPET 子表偏移 40 起是 12 字节的通用地址结构（GAS）：4 个属性字节 + 8 字节地址，**地址在偏移 44**；代码写的 48 读到的是地址的高半截（全 0）拼上下一个字段。基址 0 意味着把低地址内存当寄存器读——顺手补了一道"基址为 0 拒收"的校验（0 永远不是合法 MMIO 基址，而页 0 是正常内存，清单检查拦不住它）。

**坑 4：能力寄存器两半记反 + 64 位访问。** 基址对了，日志又显示：`period=8086A201`——这是 **ID**（厂商 0x8086、3 个定时器、64 位计数能力），不是周期！GCAP 能力寄存器：**偏移 0 是 ID，偏移 4 才是周期**（和 Linux 源码的 `HPET_ID 0x000 / HPET_PERIOD 0x004` 一致）。这个错值还恰好通过了第一版校验（2×10⁹ < 10¹¹），所以合法值区间收紧到 [1fs, 1µs]。旁边还藏着一个同类问题：HPET 的 MMIO **只接受 32 位访问**，64 位 `read_volatile` 读回来是 0（真实芯片组同款行为）——64 位数据得低字、高字分两次读再拼，读计数器还要"高-低-高"双读一致，防两次读之间计数器进位。

四层问题全部解决后，QEMU 串口日志终局：

```
acpi: hpet regs @FED00000
[acpi] hpet clock on, period=989680fs per-tick=F4240
```

989680 fs = 10ns = 100MHz，教科书值；一个滴答 = 10⁶ 刻度。再上真机——**`AH`，T 的增长速度和手表对上了，蛇正常爬**。悬案终结。

## 现在游戏里的诊断工具（使用说明）

| 操作 | 干什么 | 风险 |
|---|---|---|
| 什么都不按 | 正常玩。开机自动探测 HPET 并接管时间计数（第七幕起） | 无——探测全程地址校验，失败只打印不 panic |
| 看 `T=` | 时间计数正常就会涨，且和手表一样快 | 无 |
| 按 **H** | 复跑一遍 ACPI 探测，逐步进度上屏——探测停在哪一步，屏幕最后一行即出错位置 | 有地址校验，理论安全；重启即恢复 |
| 按 **C** | 若 `L=1`，清掉 legacy replacement 位，试着把 IRQ0 线接回去 | 成功的话 IRQ0 恢复产生中断（QEMU 复现场景用） |

诊断行字段速查：`T=秒 P± M0/1 I=xx L0/1/- A H/P/- F0/1 B7`：

- `T=`：开机秒数
- `P±`：PIT 芯片状态检测（在计数吗）
- `M`：PIC 掩码里 IRQ0 是否被挡
- `I=`：主 PIC 的 IRR（正在排队的中断）
- `L`：HPET legacy replacement 位（`1`=断开模式开启（8254 的 IRQ0 被断开）、`0`=关、`-`=没找到 HPET）
- `A`：时间计数使用哪个时钟源（`H`=HPET 主计数器、`P`=PM 定时器、`-`=都不可用退回 PIT）
- `F`：PIT 轮询兜底是否接管（`1`=接管，只见于没有 HPET/PM 的机器）
- `B7`：构建标记，烧 U 盘后核对镜像新旧用

探测的进度输出走**双通道**：屏幕上给人看，串口里留档给 QEMU 无头调试读（`-serial file:文件名` 落盘）。

## 悬案状态：结案（2026-09-20）

真机终局读数：`P+ M0 I=00 L0 AH F0 B7`——T 与手表同速，蛇正常爬。

- **修复**：时间计数维护在 HPET 主计数器上（`AH`）。固件怎么修改 PIT 都不再影响游戏——计数维护在它动不了的、频率出厂固定的 free-running 计数器上。
- **HPET 排除嫌疑**：真机 `L0`——legacy replacement 从来就没开启过，第一幕的头号嫌疑不成立。IRQ0 周期异常的根因（嫌疑仍指向 SMM 改 PIT 除数）未最终确认，但**修复不再依赖确认它**：把时间计数搬到它碰不到的时钟源上，它怎么改都无影响。这也是 Linux 的做法——不与固件对抗，改用它无法影响的时钟源。
- **架构定型**：三级降级（HPET → PM 定时器 → PIT 轮询）写进 `poll_pit_fallback()`，原来"接管产生滴答"的逻辑降级为最后一档兜底。

## 小结

这次排障最有价值的不是修复本身，是这些可复用的东西：

1. **诊断输出先于猜测**——真机上先实现能读硬件实况的诊断字段（T/P/M/I/L/A/F），一次开机锁定证据链，胜过十次盲目重启
2. **诊断代码的纪律**——零解引用启动、地址校验、进度输出；诊断工具自身崩溃，排障就从"困难"变成"无从下手"
3. **同源数据无法交叉验证**——两条参考线来自同一颗可编程时钟时，它们会一起出错；必须引入频率无法被修改的第二时钟源
4. **验证修复要连前提一起验证**——公式没错、错的是没人检查前提（第三幕）；同理，QEMU 里测不出的"前提差异"（reserved 区、清单外的 MMIO）要用日志从真机获取信息
5. **无头 QEMU + 串口落盘是高效排障手段**——进度输出双通道（屏幕+串口）之后，不碰截图、不开窗口，30 秒一轮读日志排查；四层嵌套问题就是这么逐层定位的
6. **连环问题要逐层定位**——A0 背后是四个独立的问题（reserved 区、清单外 MMIO、GAS 偏移、寄存器两半反）。每解决一层，日志就暴露下一层，比"一次修四个"的 shotgun 式调试快得多
