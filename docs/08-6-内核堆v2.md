# 08 · 内存管理（六）：内核堆 v2——让 free 真的 free

> 上一篇：[番外-真机时钟悬案](番外-真机时钟悬案.md)。番外结束，回到第八章
> 主线收尾。贪吃蛇你已经玩过了——它还顺带暴露了一个堆的隐患。本篇把
> free 做成真的，顺带补上并发保护。

## 这一章要做成什么

一句话：**把堆从"借出去就不管了"换成"借了能收回来"**，并用一个自检
程序证明回收是正确的。

要动三个文件：

- `kernel/src/sync.rs`——加一个函数：关中断临界区
- `kernel/src/heap.rs`——内部实现整体替换（对外接口不变）
- `kernel/src/main.rs`——`kmain` 里加一段自检代码

验证标准：`make run` 后串口和屏幕出现

```
heap selftest: 2 blocks, free 6193008 -> 6193008 PASS
```

这个内核目前还没有第 9 章的进程，能考堆的只有自检程序自己和贪吃蛇——
但设计是按第 9 章的负载来的：进程的创建销毁就是最典型的"频繁借还"
场景，bump 堆在那种负载下撑不住，所以这一章是第 9 章的地基。

## 先看一个正在发生的 bug

番外篇的贪吃蛇，每次吃到苹果，蛇身 `Vec` 就要长一节。`Vec` 扩容的规矩是：申请一块
**更大的**新缓冲 → 把旧数据搬过去 → **向堆归还旧缓冲**。

前三步都正常，最后一步在现在的堆这里发生了什么？看 `heap.rs`：

```rust
/// 归还。bump 版：什么都不做（下轮接 GlobalAlloc 时它必须在场）
pub fn dealloc(_ptr: *mut u8) {}
```

归还请求没有任何效果。游标只进不退，每吃一个苹果堆就永久少一块可用
内存。现在每局才漏几 KB，看不出事——但问题是结构性的：**内核里所有
`dealloc` 都是空操作**，任何长期运行的分配模式（反复开关的程序、
第 9 章随时创建销毁的进程）迟早把堆耗尽。到那天所有 `Box::new` 集体
失败，而且这类故障很难定位——出问题的代码逻辑全对，坏的是分配器本身。

要修它，问题一个接一个地来。下面四个问题，每个都逼出一块设计。

## 问题一：free 只收到一个指针，怎么知道这块内存多大？

看现在的接口：`dealloc(ptr)` 的输入只有一个裸指针，指向归还内存的
起始地址。这一块有多大？不知道。而不知道大小，就谈不上"回收"——
你连它占据的范围都圈不出来。

调用方能提供吗？不能。`Box`/`Vec` 手里同样只有指针，没有任何额外
信息可传递。

结论：**块大小必须由分配器自己存储，而且必须在分配时存好**。那么
存在哪？要求只有一条：归还时只凭那个指针就能找到。最合理的位置是
块自身的开头——指针减去一个固定偏移就是它，不需要任何全局查找结构。
这个存储块信息的结构叫**头部（header）**，16 字节：

```
一块已分配的内存的布局：

  ┌──────────┬─────────────────────────┐
  │ 头部 16B  │     载荷（返回给调用者）     │
  │  size:    │                          │
  │  本块总长  │                          │
  └──────────┴─────────────────────────┘
  ▲          ▲
  块起始       返回给调用者的指针
```

16 字节不是拍脑袋：头部要用两个字段才能干完活——一个记本块总长
（`size`，8 字节），一个留给下一章要引入的链表指针（`next`，8 字节），
两个 `usize` 正好 16。

`dealloc(ptr)` 进来先算 `ptr - 16` 定位头部，读出大小，回收才能展开。
这 16 字节是每块内存都要付出的**元数据开销**——"能回收"这个能力的
信息成本，所有真正的分配器都要付，区别只是存多存少。

接下来一条配套规矩：**块大小一律取 16 的倍数**。这就引出一个本篇
第一次出现的基础概念——**对齐（align）**。

> **对齐是什么**：一个内存地址是 n 的倍数，就说它按 n 对齐。
> 对齐要求从哪来？从数据类型来。CPU 读写多字节的数据时，要求地址
> 落在特定倍数上——比如 `u64` 要放在 8 的倍数的地址，放偏了要么
> 出错要么变慢；Rust 把每个类型的这个要求记在对齐值里，分配内存时
> 随请求一起传递（`Layout` 结构的 `align` 字段）。你写
> `Box::new(0u64)`，请求里就带着"这块内存要按 8 对齐"。
>
> 块起点按 16 对齐、大小按 16 取整，保证的是：载荷（返回给调用者的
> 那段）起点永远是 16 的倍数——16 是常见类型对齐要求的最大值，所以
> 任何 `Box`/`Vec` 的请求都能满足。

## 问题二：到哪儿找一块放得下的空闲内存？

头部解决了"归还时知道这块是谁、多大"。分配侧还有个 bump 时代不存在的
问题：以前游标后面永远是空的，不用找；现在内存里在用的块和空闲块交错
分布，空闲块散落在各处——**得有一份空闲在哪的登记**。

登记用**链表**：所有空闲块串成一条链，链上每个节点的头部里的 `next`
字段（问题一里预留的那个）指向下一个空闲块：

```
free_head ──► [空闲 64B] ──► [空闲 1.5KB] ──► [空闲 96B] ──► 空
              （链上只有空闲块；在用的块不在链上，靠自己的头部记录大小）
```

分配怎么走？**沿链扫描，取第一块放得下的**——这个策略叫首次适配
（first-fit）。放得下的判定是：这块的总长 ≥ 需求（载荷按 16 取整
+ 头部 16 字节）。找到之后切：需要的部分给调用者；剩下的部分若还够
构成一个完整块（≥ 32 字节：头部 16 + 最小载荷 16），就作为独立空闲块
留在链上；不够的话整块都给出去，剩余的零头跟载荷一起记在头部里。

归还呢？读头部得到大小，把整块挂回链上。挂的位置有个讲究——
**按地址顺序插**（链从头到尾地址递增）。这是个刻意的设计选择，
好处在下一个问题里兑现。

还剩一个细节：`alloc` 的签名是 `alloc(len, align)`，第二个参数就是
问题一里说的对齐要求。大多数请求只要 8 或 16 对齐，载荷起点天然满足；
但真有更大的——贪吃蛇画布的请求是 4096 对齐（`game.rs` 里
`Layout::from_size_align(size, 4096)`，当初为了让画布起点页对齐）。
处理办法：**返回地址先向上对齐到 `align`，头部放在返回地址前面
16 字节**。

- align ≤ 16 时，头部恰好落在空闲块原起点，一切如前所述
- align > 16 时，头部之前会垫出一段对齐缝隙。这段缝隙无法登记为
  空闲（它和任何空闲块都不相邻），成为不可复用的空洞——每个对齐
  分配最多损失 align−16 字节。画布整个生命周期只分配一两次，
  代价可忽略

这个设计还有个附带好处：头部永远紧贴在返回地址前面，`dealloc` 不需要
知道当初的对齐要求，指针减 16 就是头部。

## 问题三：内存会越用越碎

只挂链不合并的话，跑一段时间后空闲内存会碎成大量小块：空闲总量明明
够，却没有一块能放下较大的请求——这叫**外部碎片**。对抗手段是
**合并（coalesce）**：归还时检查物理上相邻的块，空闲且相邻就并成一块。

```
归还 96B 时发现：

  ... [prev 空闲 64B] [归还块 96B] [next 空闲 128B] ...

三块地址首尾相接 → 合并成一块 288B
```

问题二里"按地址顺序插链"在这里显示价值：归还时沿链找到的插入点，
`prev` 和 `next` 恰好就是物理上的左右邻居。判断能否合并只需两个比较：

- `prev 的起始地址 + prev 的大小 == 归还块的起始地址`？相邻，并入 prev
- `归还块的起始地址 + 归还块的大小 == next 的起始地址`？相邻，并入 next

一个值得想清楚的问题：**为什么不在归还时"整理内存"，把碎片挤到
一起？**因为整理意味着搬移在用的数据，搬移就要修改所有指向它们的
指针——而分配器根本不知道调用方把指针存到了哪里。所以分配器只做
不移动数据的相邻合并。碎片的彻底解决要靠更讲究的算法（伙伴系统、
slab），链表合并对我们的规模已经足够。

## 问题四：主代码改到一半，中断插进来怎么办

v1 堆的注释里有一条默认约定：单核、且中断处理函数不碰堆。第 9 章
进程一来，这个约定必然失效：主代码分配到一半，空闲链正处在改了一半的
中间态，时钟中断插入，处理函数也要分配——它在半成品上继续操作，链表
损坏。

单核机器上有一个极简且严格的解法：**临界区期间关中断**。中断是单核上
唯一的异步执行流，关掉它，临界区内就是严格的顺序执行。实现为
`without_interrupts(f)`：进入前把 RFLAGS 寄存器保存下来（它记录着
中断标志 IF 的当前值），执行 `cli` 关中断，运行 f，结束后把保存的
RFLAGS 写回。写回而不是无脑执行 `sti`（开中断），是为了支持嵌套调用：
如果外层本来就关着中断，内层退出时不得擅自把中断打开。

> CAS 自旋锁是它的多核对应物，第 9 章统一 sync 模块时再实现。

## 动手一：sync.rs 加 without_interrupts

`kernel/src/sync.rs` 追加：

```rust
use core::arch::asm;

/// 在"关中断临界区"里执行 f，结束后恢复进入前的中断状态。
/// 单核下这就是最可靠的锁：临界区内不会有任何代码插入执行。
pub fn without_interrupts<T>(f: impl FnOnce() -> T) -> T {
    let mut flags: u64;
    unsafe {
        // pushfq 把 RFLAGS 压栈，pop 读入 flags——保存中断标志原值
        asm!("pushfq", "pop {flags}", "cli",
             flags = out(reg) flags, options(nomem));
    }
    let r = f(); // 临界区：关着中断执行
    unsafe {
        // 写回保存的 RFLAGS（若本来中断就关着，这里不会误开）
        asm!("push {flags}", "popfq", flags = in(reg) flags, options(nomem));
    }
    r
}
```

两个 `options(nomem)` 告诉编译器这几条指令不碰它管理的内存，
不要据此优化掉对周围变量的访问。

## 动手二：heap.rs 替换实现

对外的 `init`/`alloc`/`dealloc`/`GlobalAlloc` 接口原样保留，
贪吃蛇等所有调用方零改动，内部实现整个替换。文件开头的状态和头部：

```rust
//! 内核堆（第二版）：空闲链表分配器。对应教程：docs/08-6-内核堆v2.md
//!
//! 每块内存前有 16 字节头部记录本块大小；空闲块串成按地址排序的链；
//! 分配走首次适配并切块，归还挂链并合并相邻空闲块。
//! 并发保护：所有操作包在 without_interrupts 里。

use crate::mm;
use crate::sync;
use core::sync::atomic::{AtomicUsize, Ordering};

const HDR: usize = 16; // 头部大小
const MIN_BLOCK: usize = 32; // 最小块 = 头部 + 16B 载荷

/// 头部。已分配块：只有 size 有意义；空闲块：还挂在链上，next 生效
#[repr(C)]
struct Header {
    size: usize,       // 本块总字节数（含头部），恒为 16 的倍数
    next: *mut Header, // 空闲链上的下一块
}

static START: AtomicUsize = AtomicUsize::new(0);
static SIZE: AtomicUsize = AtomicUsize::new(0);
static FREE_HEAD: AtomicUsize = AtomicUsize::new(0); // 链头，0 = 空链

/// 向上取整到 a 的倍数（取整载荷、对齐返回地址用的是同一个运算）
fn align_up(x: usize, a: usize) -> usize {
    (x + a - 1) & !(a - 1)
}
```

`init` 变简单了——整个堆就是一块大空闲块：

```rust
pub fn init(pages: u64) -> bool {
    let first = match mm::alloc_frame_contig(pages) {
        Some(p) => p,
        None => return false,
    };
    let start = mm::phys_to_virt(first) as usize;
    let size = (pages * mm::PAGE_SIZE) as usize;
    START.store(start, Ordering::Relaxed);
    SIZE.store(size, Ordering::Relaxed);

    // 链上只有一块：整堆
    unsafe {
        (*(start as *mut Header)).size = size;
        (*(start as *mut Header)).next = core::ptr::null_mut();
    }
    FREE_HEAD.store(start, Ordering::Relaxed);
    true
}
```

分配——问题二、三的全部设计都在这 40 行里：

```rust
/// 分配 len 字节、按 align 对齐。堆里找不到就返回 None
pub fn alloc(len: usize, align: usize) -> Option<*mut u8> {
    let len = len.max(1);
    sync::without_interrupts(|| {
        let r = align_up(len, 16); // 载荷按 16 取整

        let mut prev: *mut Header = core::ptr::null_mut();
        let mut cur = FREE_HEAD.load(Ordering::Relaxed) as *mut Header;
        while !cur.is_null() {
            let base = cur as usize;
            let cur_end = base + unsafe { (*cur).size };
            // 返回地址向上对齐；头部在返回地址前面 16 字节
            let payload = align_up(base + HDR, align);
            let header = payload - HDR;
            let end = payload + r;

            if end <= cur_end {
                // 这块放得下。剩余够构成完整块就切块，否则整段吃下
                if cur_end - end >= MIN_BLOCK {
                    let rest = end as *mut Header;
                    unsafe {
                        (*rest).size = cur_end - end;
                        (*rest).next = (*cur).next; // rest 顶替 cur 的链位
                    }
                    if prev.is_null() {
                        FREE_HEAD.store(rest as usize, Ordering::Relaxed);
                    } else {
                        unsafe { (*prev).next = rest; }
                    }
                } else {
                    // 剩余不足以自立成块，并进本次分配（头部按延伸后的大小记）
                    if prev.is_null() {
                        unsafe { FREE_HEAD.store((*cur).next as usize, Ordering::Relaxed); }
                    } else {
                        unsafe { (*prev).next = (*cur).next; }
                    }
                    unsafe { (*(header as *mut Header)).size = cur_end - header; }
                    return Some(payload as *mut u8);
                }
                unsafe { (*(header as *mut Header)).size = end - header; }
                return Some(payload as *mut u8);
            }
            prev = cur;
            cur = unsafe { (*cur).next };
        }
        None // 扫完整条链：确实没有可满足的空间
    })
}
```

读这段代码注意两点。其一，`payload` 不再是 `base + HDR` 而是
`align_up(base + HDR, align)`——这就是问题二末尾说的对齐处理；
align ≤ 16 时两者相等，走的就是最朴素的路。其二，头部记的大小是
`end - header`（不是 `r + HDR`）：对齐缝隙那段空间既不属于本次分配
的头部，也不再属于任何空闲块，它被"夹"在中间——这正是缝隙成为
空洞的代码呈现。

归还——问题三的双向合并：

```rust
/// 归还。从头部恢复块大小，按地址顺序挂回链上，并合并相邻空闲块
pub fn dealloc(ptr: *mut u8) {
    if ptr.is_null() {
        return;
    }
    sync::without_interrupts(|| {
        let mut block = (ptr as usize - HDR) as *mut Header;
        let size = unsafe { (*block).size };

        // 按地址顺序找插入点（prev/next 是物理上的左右邻居；
        // 对齐缝隙会造成"隔空邻居"，合并条件不满足就自然跳过）
        let mut prev: *mut Header = core::ptr::null_mut();
        let mut cur = FREE_HEAD.load(Ordering::Relaxed) as *mut Header;
        while !cur.is_null() && (cur as usize) < (block as usize) {
            prev = cur;
            cur = unsafe { (*cur).next };
        }

        unsafe {
            // 先挂上链
            if prev.is_null() {
                FREE_HEAD.store(block as usize, Ordering::Relaxed);
            } else {
                (*prev).next = block;
            }
            (*block).next = cur;

            // 合并前邻：prev 的末尾正好接上本块的开头
            if !prev.is_null() && (prev as usize) + (*prev).size == block as usize {
                (*prev).size += size;
                (*prev).next = (*block).next;
                block = prev; // 合并后的块以 prev 为代表
            }
            // 合并后邻：本块的末尾正好接上 cur 的开头
            if (block as usize) + (*block).size == cur as usize {
                (*block).size += (*cur).size;
                (*block).next = (*cur).next;
            }
        }
    })
}
```

最后加一个统计函数，验证时要靠它：

```rust
/// (空闲总量, 空闲块数)。分配/归还应当守恒——验证全靠它
pub fn stats() -> (usize, usize) {
    let mut total = 0;
    let mut count = 0;
    let mut cur = FREE_HEAD.load(Ordering::Relaxed) as *mut Header;
    while !cur.is_null() {
        total += unsafe { (*cur).size - HDR }; // 头部不计入空闲量
        count += 1;
        cur = unsafe { (*cur).next };
    }
    (total, count)
}
```

## 动手三：kmain 里加自检

堆对不对，不能靠"看起来没问题"。设计一条**守恒律**：反复借还各种
尺寸，空闲总量必须分毫不差地回来。`kmain` 里、贪吃蛇 `game::init()`
之前加：

```rust
// 08-6：堆自检——借还守恒律。
// 一条检查同时抓三类错：归还丢失（总量变少）、切块做错（块数异常）、
// 合并做错（块数/总量异常）。
// 指针存栈上定长数组——若存 Vec，Vec 自己的缓冲会在测量时活着，
// 污染守恒检查
let (free0, _) = heap::stats();
let mut ptrs = [core::ptr::null_mut::<u8>(); 1000];
for (i, slot) in ptrs.iter_mut().enumerate() {
    let n = 8 + (i * 37) % 512;
    *slot = heap::alloc(n, 16).expect("heap selftest: alloc failed");
}
for p in ptrs.iter() {
    heap::dealloc(*p);
}
let (free1, blocks) = heap::stats();
let msg = alloc::format!(
    "heap selftest: {} blocks, free {} -> {} {}\n",
    blocks, free0, free1,
    if free1 == free0 { "PASS" } else { "FAIL!" }
);
console::print(&msg);
serial::print(&msg);
```

## 踩坑实录

**坑 1：自检 FAIL，但分配器没有错——自检变量污染了守恒检查。**

第一版自检把 1000 个指针存进 `Vec`，跑出来 `free 6193008 -> 6184784
FAIL!`，差额 8224 字节。排查发现：`Vec` 扩容后的最终缓冲（1024 个
指针 ≈ 8KB + 头部）在测量 `free1` 时**还活着**——它本身就是自检
代码欠堆的账。守恒律没错，错在测量范围：`free0` 和 `free1` 之间
多了一份没归还的分配。

修法：指针改存**栈上定长数组**（`[*mut u8; 1000]`，8KB，内核栈
64KB 装得下），自检代码自己不再碰堆。改完立刻 `PASS`。

教训：**验证工具自身不得占用被验证的资源**。守恒律要求"测量的
前后堆的状态只差被测操作"，任何第三方分配都会破坏这个前提。

**坑 2：初版设计只支持 16 字节对齐——画布分配会直接失败（实现前
审查发现）。**

初版 alloc 的放得下判定是 `块大小 ≥ 需求 && 载荷地址 % align == 0`，
而载荷地址恒为 `块起点 + 16`。画布的请求是 4096 对齐，空闲块起点
几乎不可能恰好差 16 就落在 4096 的倍数上——整条链扫完也找不到
满足条件的块，`game::init` 会打出 `canvas alloc FAILED`。

修法就是问题二末尾说的对齐处理：返回地址向上对齐、头部跟随返回
地址。教训：**设计分配器前先盘点调用方会提出什么要求**——`grep
-rn "from_size_align" kernel/src` 一眼就能看到 4096 这个对齐要求，
不看调用方闭门造车，设计就对不上真实负载。

## 本章小结

- bump 堆的 free 是空操作：归还无效果，长期运行必然堆满——必须在
  第 9 章进程创建销毁之前解决
- 头部（header）存在的根本原因：`free` 的输入只有指针，而回收必须
  知道块大小，这个信息只能由分配器在分配时存储——存在块自身开头是
  定位成本最低的位置
- 对齐（align）：地址是 n 的倍数；要求来自数据类型，随分配请求传递。
  块按 16 对齐、大小按 16 取整，常见类型全覆盖；更大的对齐要求
  （如画布的 4096）靠"返回地址先对齐、头部跟随"处理
- 空闲链按**地址顺序**维护，合并退化为两个地址比较
- 合并不能搬移数据（分配器不知道调用方的指针存在哪里），只能合并
  物理相邻的空闲块
- 单核的并发保护 = `without_interrupts`：保存 RFLAGS → `cli` →
  执行 → 写回 RFLAGS（支持嵌套）
- 验证分配器靠守恒律：借多少、还多少，空闲总量必须分毫不差

**里程碑**：堆自检 PASS，`free` 第一次真正回收内存 ✅
