# 05 · 帧缓冲显示：在屏幕上画出第一个像素

> 上一章：[04-第一次开机](04-第一次开机.md)。内核已经在 QEMU 里点亮过一次
> （那两行串口日志）。但屏幕是 Limine 画的"工厂壁纸"，我们自己的内核
> 还一个像素都没碰过。这一章把显存拿到手，画出第一张自己的图。

运行 `make run`，你会看到一张**红绿渐变**铺满屏幕——那是你的内核往显存里
一个一个像素写出来的。这一章讲清楚两件事：**显存怎么用**，
以及**那张"需求单"是怎么从引导器手里换来显存的**。

## 本章要动的文件

| 文件 | 动作 | 干什么用 |
|---|---|---|
| `kernel/src/boot.rs` | 新建 | 手写 Limine 请求标记：接头暗号、请求单、回执结构（约 90 行） |
| `kernel/src/main.rs` | 修改 | 贴上需求单；kmain 里领屏幕、画渐变测试图 |
| `kernel/linker.ld` | 修改 | `KEEP(*(.limine_requests))`——防止需求单被链接器当垃圾删掉 |

> 顺带一段小插曲：本来想用社区现成的 `limine` crate，读了源码才发现
> 它用了 nightly 专属的语言特性，我们的 stable 工具链编不过。
> 于是决定手写——魔数和结构布局照着协议抄。坏事变好事：
> "接头暗号"从此不再是黑盒。

## 显存：一块被当成屏幕的内存

先破除神秘感：**所谓"画像素"，就是往一块普通内存里写数字**。

Limine 替我们把显卡设置好之后，屏幕变成了一个巨大的格子纸：

- 每个格子（像素）**4 个字节**，正好塞下红、绿、蓝各 1 字节外加 1 字节填充
- 往哪个格子写什么数字，屏幕那个点就亮什么颜色
- 这块内存的起始地址、屏幕宽高，Limine 通过"回执"告诉我们

写像素的地址公式（对着 `draw_test_pattern` 看）：

```
像素 (x, y) 的地址 = 显存基址 + pitch × y + 4 × x
```

新面孔 `pitch`（行距）是几个容易踩的概念之一：**一行实际占多少字节**。
它通常等于 `宽 × 4`，但显卡可能为了对齐在行尾留"走廊"——
比如屏幕 1024 宽，pitch 却是 4096+16。所以换行永远要用 pitch 跳，
不能用 `宽×4` 想当然。颜色也一样有讲究：`bpp`（每像素位数）和
RGB 各通道的掩码位置 Limine 都会告诉你，我们假设最常规的
32 位 BGR 排布，够用。

另一个细节是 `write_volatile`。这块显存不在 Rust 的任何"账本"上
（不是我们分配的变量），编译器看着我们"往没登记的地址写值"，有权把它
优化掉。`volatile` 相当于**跟编译器打招呼："这块我真的要写，别自作聪明"**。
上一章读串口状态位、这一章写显存，都是同一个道理：凡是编译器看不见的
硬件交互，都得打招呼。

## 需求单：从引导器手里换显存

显存地址从哪来？回忆第 4 章预告过的"快递柜"对话，现在拆开看细节。

### 一张请求单长什么样

`boot.rs` 里的 `FramebufferRequest` 按 Limine 协议规定的格式排布，
一共 48 字节：

```
偏移   内容            大小    说明
──────────────────────────────────────────────────
0      magic           16B    接头暗号（所有请求都一样，Limine 靠它认单）
16     id              16B    请求种类编号（"我要帧缓冲"的唯一编号）
32     revision         8B    请求协议版本
40     response         8B    回执指针，启动前是空的 ←★ Limine 会写这里
──────────────────────────────────────────────────
                                   合计 48 字节
```

暗号和编号都是协议规范写死的大常数，照抄即可。

### 单子贴在哪，Limine 才看得见

把请求单设成普通 `static` 变量还不够——**得让它落到 ELF 文件里一个
约定俗成的节区**：

```rust
#[used]
#[link_section = ".limine_requests"]
static FRAMEBUFFER_REQUEST: boot::FramebufferRequest = boot::FramebufferRequest::new();
```

`#[link_section]` 把这个变量钉进 `.limine_requests` 节；Limine 加载
内核时扫描 ELF，找到这个节，逐张读单。这招叫**用节区当信箱**——
程序和引导器之间没有函数调用，全靠文件布局传话。

然后 Limine 干两件事：把屏幕参数备好（一块 `Framebuffer` 结构，
里面是显存地址、宽高、行距……），再把**回执指针写进我们单子的
response 字段**。内核启动后一读，显存到手。

### 那个"被外部修改的变量"

这里撞上了 Rust 的规则：`static` 必须是 `Sync`（可跨上下文共享），
含 `UnsafeCell` 的类型默认不是。但我们的请求单**就是要被 Limine 从
外部改写**的——于是有了内核里第一个 `unsafe impl Sync`：

```rust
unsafe impl Sync for FramebufferRequest {}
```

这个" unsafe 实现"不是乱来，是一份担保书：启动阶段单线程、
读回执走 `read_volatile`，所以这么干是安全的。内核开发的一大常态
就是**把编译器的担保换成有理有据的人工担保**——但每张担保书都要
写清楚理由（看代码注释）。

### 双保险：别让需求单被当垃圾回收

最后一个坑，链条上最隐蔽的一环：我们的需求单**没有任何代码调用它**——
它存在的意义就是"被 Limine 从文件里读到"。可编译器和链接器清理死代码
时的逻辑恰恰相反：**没人用 = 垃圾**。两道清理关卡得分别打招呼：

- 编译器关：`#[used]`——"这个 static 别删"
- 链接器关：`linker.ld` 里 `KEEP(*(.limine_requests))`——开了
  `--gc-sections`（节区垃圾回收）后，这个节别删

少打一个招呼，需求单就消失，Limine 扫不到，屏幕就没有——而且**没有
任何报错**，只是黑屏。这类"静默失效"是裸机开发最阴的坑，所以我们把
双保险都焊死在代码里。

## 画图：三行公式的事

拿到 `Framebuffer` 之后，画图只剩地址公式和循环（见 `main.rs` 的
`draw_test_pattern`）：红随 x 渐变、绿随 y 渐变、蓝给个固定值，
`write_volatile` 写进去。跑 `make run`，左上黑、右上红、左下绿、
右下黄——一张渐变图就是"显存使用说明书"的可视化版本。

> 小坑记录：一开始想在串口里打印分辨率数字，写了 `format_args!`——
> 在 `no_std` 无堆环境里格式化输出没有标准库撑腰，这条路暂时不通
> （以后实现内核堆和日志系统时会顺手解决）。本阶段就用字符串常量。

## 本章小结

- 显存 = 普通内存，写数字就是画像素；地址公式 `基址 + pitch×y + 4×x`
- 需求单 48 字节：暗号 + 编号 + 版本 + 回执指针；靠 `.limine_requests`
  节区和引导器"隔空对话"
- 三个新 Rust 武器：`#[link_section]`（钉节区）、`UnsafeCell` +
  `unsafe impl Sync`（合法可变静态）、`#[used]` + `KEEP`（反垃圾清理双保险）
- `volatile`：跟编译器打招呼的暗语，硬件交互必备

**里程碑**：内核不靠任何引导器帮助，自己往屏幕画出了图像 ✅
