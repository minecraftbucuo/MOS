# 05 · 让内核在屏幕上画图

> 上一章：[04-第一次开机](04-第一次开机.md)。内核已经能在 QEMU 里启动、
> 往串口打字了。但屏幕上显示的还是引导器留下的画面，我们自己的内核
> 连一个像素都没画过。这一章就来解决这个问题。

## 这一章要做成什么

一句话：**让内核拿到屏幕，自己画一张图**。

我们会写两个文件、改一个文件：

- 新建 `kernel/src/boot.rs`：按 Limine 的约定格式，声明"我要使用屏幕"
- 修改 `kernel/src/main.rs`：把声明放进内核文件，再写一个画图的函数
- 修改 `kernel/linker.ld`：保护那段声明不被链接器删掉

全部写完之后，`make run` 启动，屏幕上会出现一张红绿渐变图——
那是内核直接写进显存的。有了画像素的能力，后面画字符、显示日志
就都建立在这个基础上。

## 先理清楚：谁在干什么

这一章出场的角色有三个，先把分工说清楚，后面代码才不糊涂：

**UEFI 固件**——上一章的老角色，开机第一棒。它把 Limine 装载起来就
退场了，本章不再出场。

**Limine 引导器**——它在本章干两件事：① 把屏幕设置好（选好分辨率），
② 把我们的内核文件从光盘加载进内存，然后把 CPU 交给内核。

**内核**——我们写的程序。它要做的是：从 Limine 手里拿到"屏幕的信息"
（显存从哪个地址开始、多宽、多高……），然后自己往显存里写颜色。

### 一个绕不过去的问题

细想一下你会发现麻烦：Limine 把 CPU 交给内核之后，自己就**不再运行**了。
两个先后运行的程序，没法像函数调用那样传参——Limine 结束运行后，
无法把数据递到内核手里。

两者之间唯一的媒介是**内核文件本身**：Limine 把内核文件加载进内存，
加载时它可以读取文件里的任何内容，也可以写入。所以双方约定了一套
格式——内核在文件里预留几段特殊信息，按约定的样子排布；Limine 加载时
找到这些段落，读出需求，把响应写回同一个位置。等内核开始运行，
再到那个位置读取响应。

这套约定叫 **Limine Boot Protocol**（Limine 引导协议），格式是公开
规范。我们本章写的 `boot.rs`，就是这个格式的 Rust 化。

## 屏幕的原理：显存就是一块内存

写代码之前，还得弄明白屏幕本身是怎么工作的。原理简单得出奇：

**内存里有一大块区域，每个像素占 4 个字节，里面存着这个点显示什么颜色
（红、绿、蓝各占 1 字节左右）。往这块内存的某个位置写一个数字，
屏幕对应的点就变成对应的颜色。**这块内存叫**显存**（framebuffer）。

显存按行线性排列：宽 × 高个像素，一行接一行。像素 (x, y)
的颜色存在哪个地址？

```
像素 (x, y) 的地址 = 显存起始地址 + 行距 × y + 4 × x
```

其中**行距（pitch）是一行实际占用的字节数**。它通常等于"宽 × 4"，
但显卡可能为了对齐在每行末尾留几个空字节——比如 1024 宽的屏幕，
行距却可能是 4112。所以**换行必须用 Limine 告诉我们的行距**，
不能用"宽 × 4"自己想当然。这是新手常见的坑。

起始地址、宽、高、行距——这些数字我们自己不知道，Limine 知道
（它设置屏幕的时候记下来了）。所以整个流程串起来是：

```
我们：在内核文件里声明"我要屏幕"（boot.rs + main.rs）
  ↓
Limine：加载内核时读到声明，把屏幕参数（显存地址、宽高、行距）
        写回内核文件里的约定位置
  ↓
我们：内核启动后取回参数，用地址公式往显存写颜色（draw_test_pattern）```

下面三步，就按这个顺序写。

## 第一步：boot.rs——把"约定格式"写成代码

新建 `kernel/src/boot.rs`。它回答两个问题：**"我要屏幕"这条信息怎么
排布**，以及**响应结构长什么样**。先看第一部分——协议标识与请求结构：

```rust
use core::cell::UnsafeCell;

/// 所有请求开头共用的 16 字节标识值，Limine 用它确认"这段数据按 Limine 协议排布"
const COMMON_MAGIC: [u64; 2] = [0xc7b1dd30df4c8b88, 0x0a82e883a194f07b];

/// 帧缓冲请求：按协议规定的字段顺序排布，共 5 个字段
#[repr(C)]
pub struct FramebufferRequest {
    magic: [u64; 2],                       // 16B：协议标识
    id: [u64; 2],                          // 16B：请求种类编号（标识这是帧缓冲请求）
    revision: u64,                         //  8B：这套请求格式的版本号
    response: UnsafeCell<*mut FramebufferResponse>, // 8B：响应指针的存放位置，启动前为空
}
```

`#[repr(C)]` 前面见过：按 C 语言的规则排布字段、不许 Rust 重排——
**因为 Limine 是按协议里写死的偏移量来读这些字节的**，排布必须和规范
一字不差。四个字段加起来正好 48 字节。

`id` 是哪来的？协议规范给每种请求分配了固定编号，"帧缓冲"的编号
是 `[0x9d5827dcd881dd75, 0xa3148604f6fab11b]`，构造函数里写死：

```rust
unsafe impl Sync for FramebufferRequest {}

impl FramebufferRequest {
    pub const fn new() -> Self {
        Self {
            magic: COMMON_MAGIC,
            id: [0x9d5827dcd881dd75, 0xa3148604f6fab11b],
            revision: 0,
            response: UnsafeCell::new(core::ptr::null_mut()),
        }
    }
}
```

中间那行 `unsafe impl Sync` 是本章最重要的 Rust 知识点。`response`
字段包在 `UnsafeCell` 里——因为它会被 Limine **从外部修改**（这是
整个机制的关键）。但 Rust 规定：含 `UnsafeCell` 的类型不能直接放进
`static`（编译器无法自动证明并发安全）。这里的并发安全能不能成立，
取决于两个条件，而这两个条件是可以由人验证的：

- 启动阶段只有一个线程在跑，不存在数据竞争
- 读取这个字段时用 `read_volatile`（马上讲）

条件成立，`unsafe impl Sync` 就是把这个结论显式写进代码。内核开发里
你会不断遇到这种情况：**编译器无法自动验证的事情，由程序员给出依据、
显式担责**——`unsafe impl Sync` 就是这个声明的语法。

再看第二部分——响应结构。Limine 写回 `response` 位置的是一个指针，
指向这样的结构：

```rust
/// 帧缓冲响应：Limine 写回的屏幕参数
#[repr(C)]
pub struct FramebufferResponse {
    revision: u64,                        // Limine 用的协议版本
    framebuffer_count: u64,               // 有几块屏幕（一般 1）
    framebuffers: *const *const Framebuffer, // 指向屏幕信息数组的指针
}

impl FramebufferResponse {
    /// 把裸指针变回 Rust 能用的切片
    pub fn framebuffers(&self) -> &[&Framebuffer] {
        unsafe {
            core::slice::from_raw_parts(
                self.framebuffers as *const &Framebuffer,
                self.framebuffer_count as usize,
            )
        }
    }
}

/// 一块屏幕的全部参数
#[repr(C)]
pub struct Framebuffer {
    address: *mut u8,     // ★ 显存起始地址——本章的主角
    pub width: u64,
    pub height: u64,
    pub pitch: u64,       // 行距（前面讲过的"行尾空字节"问题）
    pub bpp: u16,         // 每像素多少位（32 位 = 4 字节）
    pub memory_model: u8, // 颜色模型（RGB）
    pub red_mask_size: u8,
    pub red_mask_shift: u8,
    pub green_mask_size: u8,
    pub green_mask_shift: u8,
    pub blue_mask_size: u8,
    pub blue_mask_shift: u8,
    _resvd0: [u8; 7],     // 协议规定的保留字段
    edid_size: u64,       // 显示器信息，本章用不到
    edid: *const u8,
}

impl Framebuffer {
    pub fn address(&self) -> *mut u8 {
        self.address
    }
}
```

字段还是全部 `#[repr(C)]`、照协议排布。最后一个小方法——读取答案：

```rust
impl FramebufferRequest {
    /// 读取 Limine 写回的响应。没有响应返回 None
    pub fn response(&self) -> Option<&'static FramebufferResponse> {
        let ptr = unsafe { self.response.get().read_volatile() };
        if ptr.is_null() {
            None
        } else {
            Some(unsafe { &*ptr })
        }
    }
}
```

为什么读个指针还要 `read_volatile`？从内核代码的角度看，这个字段
**在整个程序里没有任何赋值语句写过**——修改它的 Limine 在内核启动前
就已经结束运行。不加 volatile，编译器有权推断"这内存的值一直是
null"并把读取优化掉。和上一章读串口状态是同一个道理：**凡是编译器
无法跟踪的修改来源（硬件、外部程序），读写时都必须用 volatile
显式声明**。

## 第二步：main.rs——把声明放进内核文件

boot.rs 写的是"格式"，现在要把一个真正的请求实例**放进内核文件的
`.limine_requests` 节区**（Limine 约定就到这个节里找）。
打开 `kernel/src/main.rs`，加两处：

```rust
mod boot;   // 声明新模块

// 真正的请求实例：一个 static 变量
#[used]
#[unsafe(link_section = ".limine_requests")]
static FRAMEBUFFER_REQUEST: boot::FramebufferRequest = boot::FramebufferRequest::new();
```

`#[link_section]` 把这个变量放进指定的节区；`#[used]` 告诉编译器：
"这个变量没有任何代码引用它，**但不能删**"——它存在的意义就是
被 Limine 从文件里读取。

但光编译器答应还不够，链接器还有一层清理：我们的链接配置
开了 `--gc-sections`（回收没人引用的节区），`.limine_requests` 恰恰
"没人引用"。打开 `kernel/linker.ld`，在代码段前面加一段：

```ld
/* Limine 请求区：KEEP 防止链接器把它当死代码回收 */
.limine_requests : {
    KEEP(*(.limine_requests))
    KEEP(*(.limine_requests.*))
}
```

`KEEP` 是链接脚本里"这个节必须保留"的指令。**两处声明缺一不可**——
少了任何一处，请求结构会无声无息地消失，Limine 扫不到，屏幕黑着，
而且**没有任何报错**。这是裸机开发里最难排查的一类故障，所以两处
都要做。

## 第三步：kmain——取响应、画图

声明就位后，kmain 里的逻辑很直白：取响应 → 判断有没有拿到 → 画图。

```rust
#[unsafe(no_mangle)]
pub extern "C" fn kmain() -> ! {
    let mut com1 = serial::SerialPort::new(serial::SerialPort::COM1);
    com1.init();
    com1.send_str("\n=== MOS booting ===\n");

    match FRAMEBUFFER_REQUEST.response() {
        Some(resp) if !resp.framebuffers().is_empty() => {
            let fb = resp.framebuffers()[0];    // 第一块屏幕的参数
            com1.send_str("framebuffer acquired\n");
            draw_test_pattern(fb);
            com1.send_str("test pattern drawn\n");
        }
        _ => {
            com1.send_str("no framebuffer!\n");
        }
    }

    loop { core::hint::spin_loop(); }
}
```

画图函数——就是前面那个地址公式的直接翻译：

```rust
fn draw_test_pattern(fb: &boot::Framebuffer) {
    let width = fb.width as usize;
    let height = fb.height as usize;
    let pitch = fb.pitch as usize;
    let base = fb.address();

    for y in 0..height {
        for x in 0..width {
            // x 越右越红，y 越下越绿，蓝固定——出来是张渐变
            let r = ((x * 255) / (width - 1)) as u32;
            let g = ((y * 255) / (height - 1)) as u32;
            let pixel = (r << 16) | (g << 8) | 0x40;

            unsafe {
                // 地址公式：基址 + 行距×y + 4字节×x
                let p = base.add(y * pitch + x * 4) as *mut u32;
                // volatile：显存不是本代码声明的变量，
                // 必须阻止编译器把这次写入优化掉
                p.write_volatile(pixel);
            }
        }
    }
}
```

红绿渐变是刻意选的测试图：如果显存地址、行距、颜色排布有任何一处
算错，画面会立刻变成花屏或斜纹——**从画面本身就能看出错误出在哪个
环节**。

## 跑起来

所有代码就位，现在启动：

```fish
make run
```

QEMU 窗口应该出现**红绿渐变**（左上黑、右上红、左下绿、右下黄），
旁边的串口终端打出：

```
=== MOS booting ===
framebuffer acquired
test pattern drawn
```

看到渐变图，意味着这条链第一次走通：内核在文件里按协议留下请求 →
Limine 装载时读到请求并写回响应 → 内核启动后取回显存地址 → 用地址
公式直接改写了显存。

## 踩坑实录

**坑 1：社区现成的 `limine` crate 编不过。** 本来直接用这个 crate
最省事，读它源码时发现第一行就用了 `#![feature(...)]`——**nightly
专属的语言特性**，我们的 stable 工具链直接拒绝编译，而且没有开关
可关。手写 `boot.rs` 后问题消失，代价是 90 行代码，收益是协议不再
是黑盒。

**坑 2：`no_std` 里没有格式化输出。** 想在串口打印"分辨率 1024×768"
这样的动态数字，本能地写 `format!`——但格式化机制要靠标准库/堆分配
撑腰，`no_std` 阶段还没有。本章先用字符串常量凑合，等以后实现了
内核堆和日志系统再解决。

## 本章小结

- 屏幕原理：显存就是内存，每像素 4 字节；地址公式
  `基址 + pitch×y + 4×x`，换行必须用 Limine 给的行距
- Limine 和内核通过**内核文件本身**传递信息：请求结构按协议排布，
  放进 `.limine_requests` 节区，Limine 加载时读请求、写回响应
- 本章的 Rust 新机制：`#[repr(C)]` 字段禁重排、`#[link_section]`
  指定节区、`UnsafeCell` + `unsafe impl Sync`（人工担责的声明）、
  `#[used]` + `KEEP` 两处防止清理
- `read_volatile` / `write_volatile`：凡是编译器无法跟踪修改来源的
  内存访问（硬件、外部程序），都必须显式声明

**里程碑**：内核不靠任何人代劳，亲手在屏幕上画出了图像 ✅
