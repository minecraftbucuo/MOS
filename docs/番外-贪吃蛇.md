# 番外篇：贪吃蛇——把前面所有章节串成一个游戏

## 这一章要做成什么

第八章结束时我们有了：屏幕（05/06 章）、中断和键盘（07 章）、页帧分配器和内核堆（08 章）。它们各自都验证过了，但还只是散立的模块。这一章把它们组合成一个完整程序：**一个能玩的双缓冲贪吃蛇**，跑在内核里。

要写的文件只有一个：`kernel/src/game.rs`（约 350 行）。它不发明新的底层机制，所有底层能力都是前面章节现成的：

| 谁服务它 | 给它什么 | 来自哪章 |
|---|---|---|
| `console` | 帧缓冲地址、行距、整屏尺寸，`blit_rows()` 上屏 | 05/06 章 |
| `font` | ASCII 字模表（分数、GAME OVER 文字用） | 06 章 |
| `interrupts` | 滴答数 `ticks()`——游戏的节拍和随机种子 | 07 章 |
| `keyboard` | 按键队列 `pop_key()`——方向键和重开 | 07 章 |
| `heap`（GlobalAlloc） | 整块屏外画布（真机 2.5K 屏上是 16MB） | 08 章 |

先讲两个决定整个写法的原理，再逐段读代码，最后一次性运行验证。

## 原理一：游戏循环——中断记录事件，主循环处理业务

贪吃蛇的本质需求是两件互不相关的事按各自的节奏发生：

- **蛇每 100 毫秒走一步**（时间驱动）
- **玩家随时按方向键**（事件驱动）

最直觉的写法是"键盘中断里直接改蛇的方向，时钟中断里直接走一步"——但那是错的，本项目自始至终坚持：

> **中断处理函数只记录事件，不做业务。**

理由有三：中断处理里不知道会被谁打断，跑游戏逻辑等于把长代码暴露在并发风险里；中断要短，慢了会丢键、丢拍；而且真机行为可能与模拟器不同（见本篇末尾的踩坑和《真机时钟悬案》——时钟中断在真机上压根不来，如果游戏逻辑长在中断里，游戏就跟着停了）。

所以分工是：

```
时钟中断（IRQ0） → 只做 TICKS += 1（真机上中断不可靠时，主循环改用
                    HPET/PM 定时器维护滴答计数——见《真机时钟悬案》第六幕）
键盘中断（IRQ1） → 只把扫描码翻译进队列
主循环           → 滴答变了就调 on_tick()：
                    取光按键队列 → 到步点走一步 → 重画 → 上屏
```

这是所有游戏循环乃至操作系统调度器的通用结构：**生产者（中断）只投递事件，消费者（主循环）按自己的节奏处理**。09 章的调度器就是把 `on_tick` 里的"走一步棋"换成"挑一个进程跑一段"。

## 原理二：双缓冲——为什么不能直接画显存

显示硬件每隔十几毫秒把显存整个刷上屏幕。如果直接往显存里画，刷新可能恰逢"画到一半"的时刻：擦掉的旧格子还没擦干净、新的蛇头还没画上——肉眼看到的就是蛇身一闪一闪、拖着残影。

解法是**双缓冲**：画面先画进一块屏外内存（**后备缓冲**，back buffer，就是堆上分配的那块画布），这一整帧画完，再一次性 `memcpy` 到显存。拷贝是线性的、顺序的，就算拷贝进行到一半时刷新发生，看到的也只是"上半帧是新的、下半帧是旧的"——一帧之差，人眼无感。

### 翻页翻多少：脏矩形

双缓冲还有第二个问题：**每次翻页拷多少**。显存不是普通内存——写它要经过显卡，同样拷 1 字节比普通内存慢一个数量级。整屏拷贝在 QEMU 里（"显存"就是普通内存）只要亚毫秒，在真机上一次就是几十毫秒起步。而每走一步棋，画面上真正变化的只有蛇头、蛇尾、分数那几十行像素——全量重拷 16MB，其中 99% 是未变化的像素。

所以翻页缩小成**只拷画过的行**（脏矩形，dirty rectangle）：

- 每个像素行一个脏标志（`dirty: Vec<bool>`，一行 1 字节，整屏才 1.6KB）
- 所有画图函数（`paint`/`px`）画到哪行，就把哪行的标志置位
- 翻页时把连续的脏行拼成段，一段调一次 `blit_rows(y0, y1)`，拷完清零标志

一步棋下来脏行就是三小段（蛇头 16 行、蛇尾 16 行、HUD 37 行），拷贝量从 16MB 缩到 0.7MB。这不仅是省——后篇《真机时钟悬案》会看到，整屏拷贝使主循环耗时超过一个时钟周期，轮询备用方案的时间计数会因此产生缺口，蛇因此慢成四分之一。

内存需求：QEMU 1280×800 的画布是 1280×800×4 ≈ 4MB；真机 2560×1600 是 **16MB**——这就是 08-4 章把堆做大、08-5 章让堆跟着屏幕尺寸走的原因。没有第八章，这个游戏开不了局。

## 逐段读代码

### 常量：格子、颜色、步频

```rust
/// 棋盘格子的边长（像素）。正方形，蛇和食物都占一格
const CELL: usize = 16;

/// 颜色。显存像素排布 0x00RRGGBB——红在最高字节
///（第 05 章渐变图 (r << 16) 验证过；console.rs 的旧注释写反过，已纠正）
const FOOD_COLOR: u32 = 0x00CC0000; // 红：食物，也是 GAME OVER 的标题色
const SNAKE_COLOR: u32 = 0x0000CC00; // 绿
const BG_COLOR: u32 = 0x00000000; // 黑
const TEXT_COLOR: u32 = 0x00FFFFFF; // 白
const DIM_COLOR: u32 = 0x00888888; // 灰：提示文字

/// 步频分频：时钟 100Hz，每 10 滴答走一步 = 每秒 10 步
const STEP_INTERVAL: u64 = 10;
```

棋盘不是新东西，就是屏幕本身：宽 `屏宽/CELL` 列、高 `屏高/CELL` 行。QEMU 里 80×50 格，真机 2.5K 屏 160×100 格——同一份代码，棋盘大小跟着屏幕走。

`STEP_INTERVAL` 把"滴答"换算成"步"：时钟 100Hz，每 10 拍走一步。想调游戏难度改这一个数就行。但判步点**不能**写 `t % STEP_INTERVAL == 0`——这个等值判断有个"滴答一拍一拍涨"的隐藏前提，真机上被轮询备用方案打破过（滴答跳着涨，等值判断整段漏拍），所以走的是"到点就走"：记下一个步点 `next_step`，`t >= next_step` 就走并顺延。完整经过见《真机时钟悬案》第四幕。

### 游戏状态：一个结构体说清全部

```rust
/// 游戏进行到哪个阶段了
enum Phase {
    Play,
    Over,
}

/// 游戏状态。棋盘 = 屏幕按 CELL 切成的正方形网格
struct Game {
    cols: usize,
    rows: usize,
    /// 蛇身：格子坐标列表，**末尾是蛇头**（push 进头、remove 出尾）
    body: Vec<(usize, usize)>,
    dir: (i32, i32),      // 前进方向 (列增量, 行增量)
    food: (usize, usize), // 食物所在格子
    rng: u64,             // 伪随机数状态（种子 = 开机滴答数）
    phase: Phase,
    score: usize,
    buf: *mut u8,   // 后备缓冲：屏外画布（堆上的一整块）
    pitch: usize,   // 画布行距（字节），与显存一致
    size: usize,    // 画布总字节数（整屏涂黑用）
    /// 每像素行一个"画过还没上屏"的标志。不能只记一条 [最小行,最大行]
    /// 脏带：HUD 锚在屏顶、蛇在屏中，一条带会覆盖大半个屏、造成多余拷贝
    dirty: Vec<bool>,
    /// 下一个步点在哪一拍。判步点不能用 `t % STEP_INTERVAL == 0`
    /// 的等值判断：轮询备用方案接管后滴答是跳着涨的（一次同步跨好几拍），
    /// 等值会整段漏拍——真机蛇慢成五分之一的元凶。改成"到了就走"
    next_step: u64,
    /// 自愈翻页的计数器与开关（见"自愈翻页"一节）
    heal: u16,
    heal_on: bool,
}
```

三个值得停一秒的决定：

- **`body` 的末尾是蛇头**。走一步 = `push` 新头 + `remove(0)` 旧尾，方向变更只看头两节——蛇的全部行为就用这两个操作表达，不需要链表。
- **方向用 `(列增量, 行增量)` 存**，右 = `(1, 0)`、上 = `(0, -1)`。走一步就是头坐标加上它，判墙、判身都发生在加出来之后。
- **脏标志用逐行 `Vec<bool>` 而不是一个范围**。第一版只记 `[dirty_lo, dirty_hi)` 一条带，结果 HUD 在第 8 行、蛇在 800 行，一条带把中间全部覆盖，每步照样拷 8MB——第一版修完真机上还是慢。逐行记，翻页只拷真正动过的三小段。

`buf` 是裸指针不是 `Vec`：画布就是一大块像素内存，要的是"从这开始、这么大"，Vec 的自动回收反而是累赘（见踩坑实录第二条）。`pitch`（行距）从 console 拿：显存一行实际占的字节数可能大于 `宽×4`（行尾有硬件填充），画布必须与之一致，`blit` 才能逐行对上。

### 随机数：LCG，裸机唯一的现成选择

```rust
/// 线性同余生成器（LCG）：一次乘法一次加法，输出"看着像随机"的数。
/// 裸机没有现成随机源，拿开机以来的滴答数当种子——每次开机都不同
fn next_rand(&mut self) -> u64 {
    self.rng = self
        .rng
        .wrapping_mul(6364136223846793005)
        .wrapping_add(1442695040888963407);
    self.rng
}
```

放食物要随机。没有操作系统、没有 `/dev/urandom`，最简单的伪随机就是 LCG：新状态 = 旧状态×A+B（A、B 是文献里挑选的常数，`wrapping` 表示按无符号数回绕计算，不 panic）。种子用 `interrupts::ticks()`——开机到放食物之间经过多少滴答，人按键的时刻基本不可预测，于是每次开局的蛇和食物都不同。

安全性？它不安全，可预测。但贪吃蛇的食物只需要"看着乱"，不需要密码学强度。

### 渲染原语：mark、paint、px、text

```rust
/// 登记一行"画过但还没上屏"。显存写得越少，主循环被拷贝占用的
/// 时间越短——超过一个时钟周期，轮询备用方案的时间计数就会整段漏掉
fn mark(&mut self, y: usize) {
    if y < self.dirty.len() {
        self.dirty[y] = true;
    }
}

/// 把一个格子画进后备缓冲
fn paint(&mut self, col: usize, row: usize, color: u32) {
    for yy in 0..CELL {
        // 16 行像素**每行都要登记**
        self.mark(row * CELL + yy);
        // 一行的起点 = 基址 + 像素行 × 行距 + 格子左边缘
        let row_base = (row * CELL + yy) * self.pitch + col * CELL * 4;
        for xx in 0..CELL {
            unsafe {
                let p = self.buf.add(row_base + xx * 4) as *mut u32;
                p.write_volatile(color);
            }
        }
    }
}
```

`paint` 是全模块唯一直接写内存的像素函数，其余都从它（或它的单像素版 `px`）组合出来。地址公式的层次：`格子 → 16 行像素 → 每行 16 个像素 → 每像素 4 字节`，乘 `pitch` 而不是 `宽×4`，是为了匹配显存行尾的硬件填充字节。循环里那行 `mark` 把这 16 行像素逐行登记成脏——**画和登记永远成对出现**，漏了登记的那块，屏幕上就永远是旧像素。

`write_volatile`：这块内存没有别的别名，其实不必 volatile——但 06 章写显存时用过它，这里沿用同一种谨慎，也提醒读者"这是 MMIO 风格的裸内存"。

```rust
/// 把一行 ASCII 文字画进后备缓冲（逐字取字模，亮点描 fg、暗点描 bg）。
/// col_px/row_px 是像素坐标。font.rs 的字模表本来就是公开的，直接取用
fn text(&mut self, col_px: usize, row_px: usize, s: &[u8], fg: u32, bg: u32) {
    for (i, &b) in s.iter().enumerate() {
        let glyph = &GLYPHS[b as usize];
        let x0 = col_px + i * GLYPH_WIDTH;
        for (dy, &bits) in glyph.iter().enumerate() {
            for dx in 0..GLYPH_WIDTH {
                let c = if bits & (0x80 >> dx) != 0 { fg } else { bg };
                self.px(x0 + dx, row_px + dy, c);
            }
        }
    }
}
```

逐字取字模、逐位判亮暗、亮描前景色暗描背景色——和 06 章控制台一个原理，只是画进了画布而不是直接上显存。`bg` 故意可指定：HUD 文字背后垫黑色，蛇从分数底下钻过时文字永远压在上面，画面不会花。

### 放食物：随机 + 避开蛇身

```rust
/// 把食物放到随机格子（避开蛇身占着的格子），画进缓冲
fn place_food(&mut self) {
    loop {
        let r = self.next_rand();
        let p = ((r as usize) % self.cols, ((r >> 32) as usize) % self.rows);
        if !self.body.contains(&p) {
            self.food = p;
            self.paint(p.0, p.1, FOOD_COLOR);
            return;
        }
    }
}
```

一次 LCG 输出拆两半用：低 32 位选列、高 32 位选行。撞上蛇身就再生成一次——蛇最长也就占棋盘一小半，循环很快能找到空格。

### 走一步：整个游戏的"业务核心"，其实只有 30 行

```rust
/// 蛇走一步：判死、擦尾、长头、吃食物，最后翻页上屏
fn tick(&mut self) {
    let (hx, hy) = *self.body.last().unwrap(); // 蛇头现在在哪
    // 撞墙判死：头走出棋盘就是终点（不再穿墙）
    let nx = hx as i32 + self.dir.0;
    let ny = hy as i32 + self.dir.1;
    if nx < 0 || ny < 0 || nx >= self.cols as i32 || ny >= self.rows as i32 {
        self.game_over();
        return;
    }
    let (nx, ny) = (nx as usize, ny as usize);

    let ate = (nx, ny) == self.food;
    if !ate {
        // 先移除尾巴，那格画回背景色——
        // 漏了这步就是"蛇走一路掉一节"，蛇身会越拖越长
        let tail = self.body.remove(0);
        self.paint(tail.0, tail.1, BG_COLOR);
    }
    // 咬到自己判死（判断的是移除尾巴之后的蛇身）
    if self.body.contains(&(nx, ny)) {
        self.game_over();
        return;
    }

    self.body.push((nx, ny));
    self.paint(nx, ny, SNAKE_COLOR);
    if ate {
        self.score += 1;
        self.place_food();
    }
    self.paint_score();
    // 自愈翻页（见下文"自愈翻页"一节）
    self.heal += 1;
    if self.heal >= 10 {
        self.heal = 0;
        if self.heal_on {
            // 用 HPET 给整屏重拷计时：超过一个滴答（10ms）= 真机
            // 显存写入慢，永久关闭自愈
            if let Some(t0) = acpi::hpet_now() {
                self.mark_all();
                self.blit_dirty();
                if let Some(per_tick) = acpi::hpet_per_tick() {
                    let dt = acpi::hpet_now().map_or(0, |t1| t1.wrapping_sub(t0));
                    if dt > per_tick {
                        self.heal_on = false;
                    }
                }
                return; // 整屏刚上屏，这一步不用再翻页
            }
            self.heal_on = false; // 没有钟可掐就不敢盲抄整屏
        }
    }
    self.blit_dirty();
}
```

顺序全是讲究：**先判墙**（出界直接终局）；**没吃到才移除尾巴**（吃到时尾不动，蛇才变长）；判咬自己要放在移除尾巴**之后**——蛇头进入自己尾巴尖的那一格，本该是"尾巴刚移走让出来的空格"，提前判就误判成死亡；最后 `blit_dirty()` 一次翻页——只拷这步登记过的脏行，这一步的全部渲染（擦尾、画头、重画 HUD）都在屏外完成。

翻页本身也值得一段：

```rust
/// 把登记过的行拷上屏，登记清零。连续的脏行拼成段，
/// 一段调一次 blit_rows——蛇头、蛇尾、HUD 各一小段
fn blit_dirty(&mut self) {
    let rows = self.dirty.len();
    let mut run: Option<usize> = None; // 当前脏段的首行
    for y in 0..rows {
        if self.dirty[y] {
            if run.is_none() {
                run = Some(y);
            }
            self.dirty[y] = false;
        } else if let Some(s) = run.take() {
            console::blit_rows(self.buf, s, y);
        }
    }
    if let Some(s) = run {
        console::blit_rows(self.buf, s, rows);
    }
}
```

一遍线性扫描：连续的脏行攒成一段，遇到干净行就把整段交出去。终局清屏、重开摆棋是"真整屏都变了"，走 `mark_all()` 把标志全部置位，同一段代码自然退化成整屏拷——同一段代码覆盖两种场景。

### 自愈翻页：修复 QEMU 模拟显示的残影

脏矩形在真机上完美，在 QEMU 里却暴露一个新问题：**蛇走过的地方偶尔残留一条细绿渣**。原因在模拟显示的工作方式——QEMU 的模拟显卡只重画"检测到过写入"的像素行。脏矩形翻页只写小段显存，某一行如果恰好在拷贝中途被模拟器刷新捕获，那行就定格在半更新的状态；而脏矩形接下来不会再写它，旧像素就永远留在屏上。旧版整屏翻页每步全量重写，即使这次被捕获，下一步也会覆盖，所以从未出现这个问题。

修法是**自愈翻页**：每 10 步（约 1 秒）把整屏重新登记、整屏重拷一遍，把可能的陈旧行覆盖掉。但整屏重拷在真机上会让旧问题重现（16MB 慢显存，见《悬案》第三幕），所以拷之前用 HPET 计时：整屏重拷超过一个滴答（10ms）= 显存写入慢的机器，自愈永久关闭——真实显示每帧都重读显存，本来就没有残影，不需要这个机制。没有 HPET 可计时的机器同样不做盲目整屏重拷。QEMU 里"显存"就是内存，几毫秒拷完，自愈保留。

这段代码顺带示范了一个思路：**对环境差异不靠猜测，按实测结果选择路径**——同一条逻辑，拷得快就保留，拷得慢就自动停用，不需要编译期开关也不需要配置项。

### 终局与重开：不重新分配

```rust
/// 原地重开：重置状态、重画第一帧。注意不能重新 init——
/// bump 堆不回收，每死一次就分配一块新画布的话，两局堆就见底了
fn reset(&mut self) {
    self.body.clear();
    // ……重置状态、清屏、画蛇和食物、blit……
}
```

注释里那句对应 08-4 章 bump 堆的限制：内存只进不出，`free` 是空操作。所以画布**只在开局分配一次**，重开是原地复用——状态清零、画布涂黑、重画第一帧。

### on_tick：主循环的对接点

```rust
/// 主循环每个滴答调一次。先消化按键队列（中断攒下的事件），
/// 再按阶段处理：Play 里到步点走棋；Over 里等空格重开
pub fn on_tick(t: u64) {
    // 方向键走扩展码（0xE0 前缀），WASD 走普通字符码——两条路都通
    let mut restart = false;
    while let Some(k) = keyboard::pop_key() {
        match k {
            keyboard::KEY_UP => set_dir(0, -1),
            keyboard::KEY_DOWN => set_dir(0, 1),
            keyboard::KEY_LEFT => set_dir(-1, 0),
            keyboard::KEY_RIGHT => set_dir(1, 0),
            b'w' => set_dir(0, -1),
            b's' => set_dir(0, 1),
            b'a' => set_dir(-1, 0),
            b'd' => set_dir(1, 0),
            b' ' => restart = true,
            // 诊断键（真机时钟悬案排障用，可选）：H 探测 HPET，C 清位尝试
            b'h' => acpi::probe(),
            b'c' => acpi::try_clear(),
            _ => {}
        }
    }
    // ……到步点走棋 / 空格重开……
    if let Some(g) = GAME.get().as_mut() {
        match g.phase {
            Phase::Over => {
                if restart {
                    g.reset();
                }
            }
            Phase::Play => {
                // 到点就走，不用等值判断（原因见 STEP_INTERVAL 那段）
                if t >= g.next_step {
                    g.next_step = t + STEP_INTERVAL;
                    g.tick();
                }
            }
        }
    }
}
```

`while let Some(k) = pop_key()` 一次取光积压的按键（中断可能在两次 on_tick 之间攒了不止一个）。`set_dir` 里有一道防 180 度调头的检查——而且光查"是否与当前方向相反"不够：一步之内连按两键（比如先按 w 再按 a）能组合出反向绕过检查，所以它实际验证的是"新方向走一步不许落在蛇头后一节（第二节身体）的格子上"。

H 和 C 两个键是真机时钟悬案的诊断工具，与本游戏无关，不按即不存在。

### init：画布从堆里来

```rust
pub fn init() {
    let (w, h) = console::pixel_size();
    let (pitch, size) = console::canvas();
    if w == 0 || h == 0 || size == 0 {
        // 没有屏幕（个别真机固件不响应 Limine 的 framebuffer 请求）。
        // ……不开局，让屏幕保持引导器留下的样子，别无声无息地挂死
        return;
    }
    let (cols, rows) = (w / CELL, h / CELL);

    // 后备缓冲：整块屏外画布，从堆里要（堆已按屏幕尺寸扩好）
    let buf = unsafe { alloc(Layout::from_size_align(size, 4096).unwrap()) };
    if buf.is_null() {
        // 画布跟屏幕一样大，屏幕越大要得越多——真机 2.5K 屏的画布 16MB，
        // 堆开小了这一步就失败。上屏报错，绝不无声无息地不开局
        //（这次的教训：静默失败最难查，屏幕停在启动文字上，与死机无法区分）
        console::print("game: canvas alloc FAILED!\n");
        return;
    }
    // ……建 Game、reset 摆第一帧……
}
```

两道防御各对应一次真机故障（详见踩坑实录）：屏幕尺寸为 0 时不开局，是怕 `place_food` 里 `% self.cols` 除以零；画布分配失败必须在屏幕上**打印报错**，因为上一版静默 `return` 让"堆不够"伪装成了"死机"。

make run

预期看到：

1. 启动文字滚过后出现黑色游戏画面：左上角 `SCORE 0` 和灰色诊断行，屏幕中间一条向右爬的四节绿蛇，一颗红色食物
2. **不碰键盘**，蛇以每秒 10 格的速度自己爬；串口每秒打印一行 `[timer] Ns`
3. 方向键 / WASD 转向，吃食物变长、分数 +1
4. 撞墙或咬到自己 → 居中红色 `GAME OVER` + 分数 + `SPACE TO RESTART`
5. 空格重开，画面恢复第 1 步的样子

常见失败：

| 现象 | 原因 |
|---|---|
| `game: canvas alloc FAILED!` | 堆没跟上屏幕尺寸——检查 main.rs 里堆页数是否按 `console::canvas()` 算的 |
| 蛇不动、按一下动一下 | 时钟中断没来。QEMU 里不该发生；真机上见《番外-真机时钟悬案》 |
| 画面闪烁有残影 | 渲染没走画布、直接画了显存 |
| 蛇越走越长 | `tick` 里漏了收尾擦尾那两行 |
| QEMU 里蛇走过拖细绿渣 | 自愈翻页没生效（正常应在 1 秒内抹平）；真机不需要自愈 |

## 踩坑实录

**坑 1：真机画布 16MB，QEMU 里 4MB，堆按 QEMU 配。** QEMU 一切正常，真机开局静默失败——因为堆只有 4MB 出头，装不下 2.5K 屏的画布。更糟的是失败路径是无声 `return`，屏幕停在启动文字上，看上去像死机。修法：堆大小跟着屏幕尺寸走 + 失败必须上屏喊出来。**静默失败比崩溃难查十倍，因为它的现场是干净的。**

**坑 2：重开不能重新分配。** 一开始 `reset` 里图省事重新走了一遍分配逻辑——bump 堆不回收，两局就见底。大块内存只在初始化时分配一次，之后一直原地复用。

**坑 3：真机上蛇"按一下键才动一下"。** 这不是本章的坑，是下一篇《真机时钟悬案》的开端——真机的时钟中断一次都没来过，主循环的 `hlt` 只有键盘能唤醒。完整推理和修复（PIT 轮询备用方案）在《番外-真机时钟悬案》。

**坑 4：真机上蛇自己爬，但慢得可观；QEMU 里一切正常。** 轮询备用方案记时间的公式有个前提："两次轮询间隔小于一个 PIT 周期（10ms）"。真机每步棋整屏拷 16MB 慢显存，一拷几十毫秒——主循环耗费在拷贝里的这段时间，PIT 计数器已经多次重装，而差值计算最多只能累计一个周期的增量。QEMU 里画布 4MB、"显存"是普通内存，前提永远成立，所以怎么测都测不出来。两处修改：脏矩形翻页（拷贝量缩 20 倍）+ 接管时把 PIT 周期放宽到 54.9ms（扩大量程）。教训比代码有价值：**验证一个修复，要连它注释里写的那个前提一起验证**——公式没错，错的是没人检查前提在真机上是否成立。全过程见《番外-真机时钟悬案》第三幕。

**坑 5：脏标志只标了格子的首尾两行，蛇变成两条移动的边线。** 脏区方案从"一条 [lo,hi) 脏带"改成"逐行标志"时，`paint` 里标两端的老写法被照搬了——标两端对脏带是对的（两端定出一条带），对逐行标志却只登记了 16 行像素里的 2 行。结果：屏幕上蛇只剩上下两条 1 像素的绿边线在爬，旧身体像素残留屏上，食物吃不掉（那格中间的像素永远不更新）。教训：**一个表示换成另一个表示时，它的每个调用点都要重新审一遍，不能因为"都是标脏"就默认等价**。

**坑 6：量程扩容后蛇慢成五分之一，步点判断漏拍。** 轮询备用方案的滴答本来一拍一拍涨，等值判断 `t % 10 == 0` 没问题；第三幕把 PIT 周期放宽到 54.9ms 后，滴答改成跳着涨（一次同步跨 5.49 拍），等值判断命中不了中间的步点。两处修改：轮询每次都同步滴答（不攒到重装）+ 游戏改"到点就走"（`next_step` 记下一拍，`t >= next_step` 就走）。这是"一个修复打破另一个修复的隐藏前提"的实际案例，见《悬案》第四幕。

**坑 7：QEMU 里蛇走过拖一条细绿渣。** 模拟显卡只重画"检测到过写入"的行——脏矩形翻页中被刷新捕获的半更新行，之后没人再写它，旧像素永远留屏。旧版整屏翻页每步全量重写，所以从未出现这个问题。修法：自愈翻页——每 10 步整屏重拷一遍，拷之前用 HPET 计时，超过 10ms（真机显存写入慢）自愈永久关闭。教训：**换渲染策略要考虑显示端的行为特性，QEMU 的模拟显示和真实显示不同**；以及对环境差异按实测结果分流，见"自愈翻页"一节。

这一章没有新的底层机制，却把 05~08 章的全部产出组合成了一个完整程序：帧缓冲提供像素画布，字模表提供字形数据，中断提供时间基准与键盘输入，内核堆提供了 16MB 的后备缓冲。更重要的是 `中断只记事件、主循环处理业务` 这个结构——把 `on_tick` 里"走一步棋"换成"挑一个进程跑一段"，它就是 09 章的调度器。
