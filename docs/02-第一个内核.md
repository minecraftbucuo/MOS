# 02 · 第一个内核：从"程序"到"内核"

> 上一章：[00-启动流程](00-启动流程.md)。这一章我们写出第一批真正的代码，
> 让内核编译成一个合法的 64 位 ELF 文件。它暂时只会空转，但地基从此立起来了。
>
> **本章你将搞懂**：内核和普通程序到底差在哪、链接脚本是干什么的、
> CPU 的第一条指令为什么必须是汇编，以及两个新手必踩的坑。

## 0. 先想清楚两个问题

### 问题 1：引导器（Limine）怎么知道把内核放到内存哪里、从哪开始执行？

普通程序是操作系统替它读 ELF 文件、分配内存的。但现在我们自己就是操作系统，
没人伺候我们——所以这些信息必须由**内核自己声明**。声明分两层：

- **链接脚本**（`linker.ld`）：规定内核各个部分放在哪些虚拟地址，入口是哪个符号
- **ELF 头**：链接器按脚本的指示生成，Limine 读它就知道"这段加载到哪、跳到哪"

### 问题 2：内核的第一条指令为什么不能用 Rust 写？

因为任何 Rust 函数编译后的开头都要**用栈**（保存寄存器、压栈），而引导器交权时
栈指针 `rsp` 指向哪里是不确定的——一用就崩溃。所以第一条指令必须是汇编：
**自己搭一个栈，然后 `call` 进 Rust 世界**。

我们用 `file` 和 `objdump` 命令可以亲眼验证这一切（见第 5 节）。

## 1. 项目结构

这一章只涉及 4 个文件：

```
kernel/
├── Cargo.toml          # crate 清单：叫什么名字、用什么配置
├── .cargo/config.toml  # 编译配置：目标平台、链接参数
├── linker.ld           # 链接脚本：内核的内存布局图纸
└── src/main.rs         # 入口汇编 + Rust 入口
```

## 2. 敲下 `cargo build` 之后发生了什么（先懂流程，再看细节）

理解这一节，后面所有章节的构建过程就都通了。4 个源文件按下面的顺序轮流登场：

```
你: cargo build
      │
      ▼
① 读 kernel/Cargo.toml ────────── 「这个项目是什么」
      │    名字叫 mos-kernel，源码在 src/，panic 时直接中止
      ▼
② 读 kernel/.cargo/config.toml ── 「用什么姿势编译」
      │    目标平台: x86_64-unknown-none（裸机，无操作系统版）
      │    编译参数: 链接时用 linker.ld；地址静态定死（不是 pie）
      ▼
③ rustc 编译 src/main.rs ──────── 「翻译」
      │    把 Rust 翻译成机器码，产出中间产物（目标文件 .o）
      │    注意：此刻所有地址都是【占位符】，还没定下来！
      ▼
④ 链接器 rust-lld 上场 ────────── 「拼装 + 安门牌」
      │    一手拿着 .o，一手拿着 linker.ld 这张图纸：
      │    - 把 .text/.rodata/.data/.bss 各归各位
      │    - 图纸说基址 0xFFFFFFFF80000000，就都摆到高地址
      │    - 把占位符填成真实地址（= 第 6 节踩的"重定位"坑）
      │    - 在文件开头写好 ELF 头："入口在 _start"
      ▼
⑤ 成品: target/x86_64-unknown-none/debug/mos-kernel
```

一句话记住每个文件的身份：

| 文件 | 身份 | 一句话 |
|---|---|---|
| `src/main.rs` | 内容 | 内核的代码本体 |
| `Cargo.toml` | 名片 | 项目叫什么、怎么配置 |
| `.cargo/config.toml` | 点菜单 | 告诉编译器"给裸机编译，别当普通程序" |
| `linker.ld` | 装修图纸 | 代码和数据各放内存哪个位置 |
| `target/` | 仓库 | 成品和中间产物都堆这里 |

**验证你理解了**：成品文件在 `file` 命令下显示 executable，但在 Linux 里
运行不了（`./mos-kernel` 会报错）。为什么？

因为它虽然长得像普通可执行文件（ELF 格式），但它期望的世界不存在：
Linux 不会加载它（它不是给 Linux 编译的），只有 Limine 会按它 ELF 头里的
说明把它放进裸机内存。**它不是"跑在操作系统上的程序"，
它是"等着变成操作系统本身的文件"**。

## 3. 链接脚本：内核的"装修图纸"

链接器（linker）的工作是把编译产物拼成最终的可执行文件。拼之前它需要一张图纸：
**哪个节（section）放哪个地址**。普通程序的图纸是操作系统默认提供的，
内核的图纸必须自己画（`kernel/linker.ld`）：

```ld
ENTRY(_start)                  /* 入口符号：Limine 跳转到 _start */

KERNEL_BASE = 0xFFFFFFFF80000000;

SECTIONS
{
    . = KERNEL_BASE;           /* "." 是位置计数器，拨到内核基址 */

    .text : ALIGN(4K) {        /* 代码段，4K 对齐（和内存页大小一致） */
        KEEP(*(.text.entry))   /* 入口代码排最前，KEEP 防止被优化掉 */
        *(.text .text.*)
    }

    .rodata : ALIGN(4K) { *(.rodata .rodata.*) }  /* 只读数据 */
    .data   : ALIGN(4K) { *(.data .data.*) }      /* 可写数据 */
    .bss    : ALIGN(4K) {                        /* 未初始化数据 */
        __bss_start = .;
        *(.bss .bss.*)
        __bss_end = .;
    }
    ...
}
```

### 搬家师傅的分类收纳

细看这张图纸之前，先认识"节"（section）——图纸上的基本房间。

编译器像一位讲究的搬家师傅，装车前会把东西分门别类装进贴好标签的箱子：
机器码进 `.text` 箱，字符串常量进 `.rodata` 箱，有初值的全局变量进 `.data`
箱，没初值的（比如一个大数组）进 `.bss` 箱。链接脚本做的事，就是规定这些
箱子在内存大楼里各住哪一层。

`.bss` 箱有个省钱的小聪明：既然里面的东西全是"零"，那文件里干脆不装内容，
只记下"这里需要一片多大的清零空间"，等搬到内存时现场清零。
**不占内核文件一个字节。**

### 把内核的家安在顶楼

再看基址 `0xFFFFFFFF80000000`——64 位地址空间的顶楼。为什么不把内核放在
一楼（低地址，比如物理内存开头的 0x100000）？

因为一楼是好铺面，将来要整层租给用户程序；内核自己搬到顶楼去住，
楼上的住户和楼下的租客就永远不会为了地盘打架。Linux 也是这么住的
（它的内核基址恰好就是 `0xFFFFFFFF80000000`，我们直接沿用这个门牌）。

有人会问：顶楼地址这么大，可我的电脑没有那么多内存，住得下吗？
住得下——因为这是**虚拟地址**，不是真实的门牌。虚拟地址像快递单上的
"收件人姓名"，还要经过**页表**这位翻译员查表换成"实际住址"（物理地址）
才能送到。Limine 退场前已经把顶楼到真实内存的翻译表建好了，
我们直接拎包入住。

## 4. 入口代码：第一条指令

`kernel/src/main.rs`（完整讲解见代码注释，这里提取骨架）：

```rust
#![no_std]   // 不链接标准库：没有操作系统托底
#![no_main] // 没有 main：入口由链接脚本的 ENTRY(_start) 决定

// 内核启动栈：16 字节对齐（x86-64 ABI 要求），放在 .bss 段
#[repr(align(16))]
struct BootStack([u8; 64 * 1024]);
static BOOT_STACK: BootStack = BootStack([0; 64 * 1024]);

#[unsafe(no_mangle)]              // 符号名保留为 _start，不被 Rust 改名
#[link_section = ".text.entry"]   // 放进链接脚本指定的入口节
#[unsafe(naked)]                  // "裸函数"：不生成任何函数序言
pub extern "C" fn _start() -> ! {
    naked_asm!(
        "movabs rax, {stack}",        // 栈的地址进 rax（64 位立即数装得下高地址）
        "lea rsp, [rax + 64*1024]",   // rsp 指向栈顶（栈向低地址生长）
        "xor ebp, ebp",               // 清帧指针：表示"没有上层调用者"
        "call {kmain}",               // 进入 Rust 世界
        "2:", "hlt", "jmp 2b",        // 万一 kmain 返回，停机兜底
        stack = sym BOOT_STACK,
        kmain = sym kmain,
    );
}

#[no_mangle]
pub extern "C" fn kmain() -> ! { loop { core::hint::spin_loop(); } }

#[panic_handler]                    // no_std 的强制要求：panic 逻辑自己接盘
fn panic(_info: &PanicInfo) -> ! { loop { core::hint::spin_loop(); } }
```

几个关键概念，逐个说透：

**`#[naked]` 裸函数**：普通函数编译后开头有一段"函数序言"（保存寄存器、
调整 rsp）——好比服务生上菜前先铺桌布。可现在连桌子都还没有（栈不存在），
铺桌布这个动作本身就会踩空。naked 让函数内容 100% 由我们的汇编组成——
"不铺桌布直接上菜"，入口函数必须这样。

**`extern "C"`**：用 C 调用约定。Rust 默认的调用约定是"实现细节"、随时可变，
只有 `extern "C"`（System V ABI）是跨工具链的稳定契约，链接脚本和引导器
才能正确对待这个符号。

**`sym` 操作数**：`sym BOOT_STACK` 表示"把这个符号的地址嵌进汇编"，
相当于汇编里的立即数寻址。`call {kmain}` 同理。

**`#[panic_handler]`**：标准库里的 panic 逻辑（打印消息、回溯调用栈）
依赖操作系统，现在没有，编译器强制我们自己实现。当前是死循环，
后面升级为"打印错误位置并停机"。

## 5. 编译与验证

一次性准备（下载 x86_64 裸机目标的预编译核心库）：

```fish
rustup target add x86_64-unknown-none
```

编译 + 验证：

```fish
cd kernel
cargo build
file target/x86_64-unknown-none/debug/mos-kernel
# 期待: ELF 64-bit LSB executable, x86-64, statically linked ...

objdump -d target/x86_64-unknown-none/debug/mos-kernel | head -12
```

反汇编输出（你的内核前几条指令！）：

```
ffffffff80000000 <_start>:
ffffffff80000000:  48 a1 ...  movabs 0xffffffff80001000,%rax   ← 栈地址进 rax
ffffffff8000000a:  48 8d ...  lea    0x10000(%rax),%rsp        ← rsp = 栈顶
ffffffff80000011:  31 ed      xor    %ebp,%ebp
ffffffff80000013:  e8 ...     call   ffffffff80000020 <kmain>  ← 进入 Rust
ffffffff80000018:  f4         hlt                               ← 兜底
```

能看到 `_start` 落在 `0xffffffff80000000`——图纸定下的位置，说明链接脚本生效了。

## 6. 新手必踩的两个坑（我们亲自踩过）

### 坑 1：`unsafe attribute used without unsafe`

```
error: unsafe attribute used without unsafe
  --> src/main.rs:29:3
   |
29 | #[naked]
   |   ^^^^^ usage of unsafe attribute
```

**原因**：`#[naked]`、`#[no_mangle]` 这类属性能绕过编译器的常规保证
（naked 直接改变函数的机器码结构），属于"危险属性"。新版 Rust 要求
显式写成 `#[unsafe(naked)]`——和 `unsafe {}` 块同一思想：
**危险的地方必须写得扎眼**。

**修法**：按编译器提示包一层 `unsafe(...)` 即可。

### 坑 2：`relocation R_X86_64_32S cannot be used`（链接错误）

**背景概念——重定位（relocation）**：链接器拼接各目标文件时，要把代码里
"这里填某符号的地址"的占位符替换成真实地址。`R_X86_64_32S` 表示这个
占位符只有 **32 位宽**。

**原因**：我们写的 `lea rsp, [栈地址 + 64K]`，寻址方式只装得下 32 位地址，
而栈的地址 `0xFFFFFFFF80001000` 需要 64 位。另外链接命令默认带了
`-pie`（位置无关可执行文件，给普通程序准备的），和高地址内核冲突。

**修法**（两处）：

1. 汇编改成先用 `movabs`（专装 64 位立即数）把地址搬进 `rax`：
   ```asm
   movabs rax, {stack}
   lea    rsp, [rax + 64*1024]
   ```
2. `.cargo/config.toml` 加 `" -C relocation-model=static"`：
   内核地址链接时就定死，不做位置无关。

> **经验**：裸机开发一半的报错都是"地址宽度/对齐/加载位置"问题。
> 看到重定位错误，先想"这个数装得下吗、对齐了吗、链接地址和加载地址一致吗"。

## 7. 本章小结

- 内核 = 特殊的程序：`no_std`（无标准库托底）、入口自定义（链接脚本说了算）
- 链接脚本是内存布局图纸；"高地址内核"是主流 OS 的通用布局
- 第一条指令必须汇编：建栈 → call 进 Rust
- 两个高频坑：unsafe 属性新语法、32 位寻址装不下 64 位地址

**里程碑**：`cargo build` 产出高地址、静态链接的 64 位内核 ELF ✅
